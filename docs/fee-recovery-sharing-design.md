# 恢复补充资料的引用共享与容量判断

2026-10-27，第九十九轮。目标是验证完整候选中重复原文能否可逆共享，并明确是否足以解决既有超限。结论为**容量路线不接入：保留现有恢复方式，优先推进已支持规模的完整工作台恢复**。本轮没有生成新的完整恢复文件或安装运行控制器。

## 原型与数据保全

[共享模块](../tools/fee-recovery-sharing.ts)只对第九十八轮补充profile的完整字符串值建立字典。1024 UTF8字节以上的相同字符串按原文相等共享，不解析、规范化或改写其中的JSON；不同空白、BOM、换行和未知历史保持。结构容器仍逐个展开，不恢复旧对象身份，数字、负零、null和空串分别表示。独立协议种类为`INTERNAL_FEE_RECOVERY_SHARED_SUPPLEMENT_PROTOTYPE`0.1，明确不是恢复归档。

原20项保留根、完整捕获、生产校验和原Node协议继续独立。共享表示经浏览器解码、独立Node token解码得到完全相同的补充JSON；原捕获的5份编码另经未改动Node协议解码再编码核对。原业务私有确认、补丁、读取任务和客户确认均不因此获得执行资格。

| 预算 | 含义及本轮处理 |
|---|---|
| 原来源128 MiB、300000节点、深度32 | 原保留根/完整捕获继续按原规则检查；4/8拒绝后不继续共享 |
| 补充展开128 MiB、300000节点、深度32 | 从引用表核算完整展开量，先检查后构造对象；重复引用按每次出现计入 |
| 原始载荷256 MiB | 共享中间表示属于未压缩数据体；计算实际JSON字节，超限前拒绝整体序列化 |
| 最终恢复文件64 MiB | 沿用原格式定义；本轮不创建最终恢复文件，不凭中间表示或gzip正文大小授予导入资格 |
| 原完整聚合128 MiB | 原完整捕获compact UTF8与补充展开UTF8相加；引用共享不改变该数值或判断 |

gzip比较只统计同一补充JSON与共享中间表示的原生gzip文本体，包含各自gzip头尾，不包含完整恢复文件的原来源、JSON外层、base64和哈希字段。观察流单独设64 MiB输出计数上限，不代表最终文件已通过。原生缓冲、实际峰值内存和生产耗时未测量。300000节点、32深度及128 MiB展开预算也不是物理RAM峰值承诺。

## 为什么不作为容量修复接入

待确认候选的原捕获32,776,828字节，补充资料110,237,566字节，总计143,014,394字节；即使补充表示更小，展开后仍超过134,217,728。旧恢复格式在同一实际状态下仍返回`LOGICAL_SIZE`。改变判断需要另行设计新的预算语义并证明安全，不能把文件压缩率当作容量改善。

实际重复的大字符串主要出现在`envelope_ui.workbench_result`。许多备份内部的重叠内容并不是相等的完整字符串；本轮不解析或改写这些不透明原文以制造收益。基础、正式采用和应用后状态的原始共享表示都有额外开销，不能默认使用该原型替换现行格式。

第100轮优先为已能完整保全的小规模资料设计新所有者上的安静安装与用户恢复入口，显示恢复清单、未提交内容及需重新输入的浏览器数据；失败保留当前工作台。完整预览、当前明确确认、一次费用/回执、正式交接和客户隔离通过后才考虑运行接入。超限资料继续明确拒绝，后续容量方案单独验证。见[本轮验证](fee-recovery-sharing-validation.md)、[既有恢复格式](fee-recovery-format-design.md)和[开发计划](development-stages.md)。
