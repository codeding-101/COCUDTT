# 业务身份、应用封套与消费历史：实现前设计

2026-10-18，第七十一轮。承接[只读应用提案](fee-application-proposal-validation.md)和[事务边界](fee-application-design.md)。本轮确定拟议协议并加入独立缩减反例；**没有生产封套解析器、迁移函数、Schema、存储、运行入口或费用写入**。下列1.0字段是待实现契约，不是当前可打开的文件。

## 身份与历史原点

拟议独立格式为`INTERNAL_FEE_APPLICATION_ENVELOPE / 1.0`；不升级项目0.8/0.9、配对1.0/1.1、成分1.0或精度1.0。封套明确持有`envelope_id`、`business_id`、`revision`、`history_origin`和完整原始资料。business_id来自新封套的明确流程，不从项目名称、pair_id、文件名、术语或旧同名扩展推导。

| 进入方式 | 历史状态与行为 |
|---|---|
| 打开旧项目/配对 | 只预览原资料。明确采用封套后为UNKNOWN_IMPORTED；记录来源原文，不建立“全未消费”证明 |
| 旧内存/异常备份 | 恢复候选资料，不当作应用文件。已有费用不能反推或补造回执 |
| 独立新建业务 | 明确声明新业务、建立新业务/封套/来源身份、撤销已知确认后才建立NEW_DECLARED原点；这是用户声明的本地谱系，不是真实订单认证 |
| 打开有效新封套 | 重新验证全量资料和历史，预览后明确采用；不因文件可解析自动安装或重放费用 |
| 历史缺失、坏引用、未知版本 | 保留原文供备份，阻断应用；不降级为空历史、不按“修复”清空已消费记录 |

UNKNOWN_IMPORTED不能通过改revision、项目名、外层hash或“我确认”字段变成NEW_DECLARED。已采用的当前谱系若丢失历史，恢复同一谱系的完整可信候选；或明确建立独立新业务、重建相关来源身份及全部确认。后者不证明现实订单从未重复。本工具不提供跨文件、设备或现实订单的全局去重保证。

## 一个完整封套，资料与历史一起保存

拟议外层字段包括：kind/version、双身份、revision、history_origin、`current_sources`、`ledger_json`、`archives`、`content_sha256`。不允许未知活动字段或未来版本；旧资料内部的未知扩展仍在原始JSON中惰性保存，不提升成活动字段。

外层与ledger的业务身份/原点必须相同，不能把合法旧回执拼进另一个业务。语义变更递增revision，上限拒绝；只改变外层JSON排版不产生新业务或新历史，但完整原文租约仍变化。编辑/采用/恢复须携带身份、revision、content_sha256、当前原文及操作代次，异步前冻结，完成后重验，不凭revision单字段覆盖。

- `current_sources`保留当前项目、账单和各工作区的完整原文与明确角色。原项目与当前账单不能由历史配对的内嵌快照偷偷覆盖。配对/成分/精度来源允许缺失或失配，但必须列出待核状态，不能假装完整。
- `ledger_json`是完整历史清单的原文：业务身份、原点快照引用、有序回执引用和累计退休目标。每个引用绑定不可变归档原文SHA-256；生产解析器须遍历并验证整个引用闭包，不能信任一张只有hash/计数的清单。
- `archives`按SHA-256保存一次不可变JSON原文。相同原文字节可共享；文件名、revision或数值等值不能代替原文身份。必须同时验证hash、引用角色/真实格式、完整源关联和历史顺序；只有hash相等不够。
- 原点、每次完整计划、五类来源、提交前ledger清单原文、前/后项目与账单payload及回执均在闭包内。历史配对/附件/精度文件按各自原快照验证，不要求它们与后来的当前项目仍匹配；相对当前的失配仍明确显示。
- 财务payload拟为完整`{project_json,bill_json}`原文容器，不包含回执、文件状态或外层hash。它保守绑定全部项目/账单文字，修改元数据也可导致旧回执相对当前待核；不靠字段白名单遗漏费用。

保存是冻结整个封套的一次用户交付，不分别保存“财务”和“账本”两个文件再承诺原子性。实际内存提交、浏览器缓存和磁盘保存仍是独立资源，遵守原事务设计的提交前/后故障分界。

## 不自引用的回执与归档图

每份回执拟包含transaction_id、sequence、business_id、前一回执指纹、完整计划引用、完整来源引用、提交前ledger清单引用、前/后payload引用、逐行消费/引用记录及entry_sha256。计划包含完整业务动作与字段原值，不只金额；重复transaction_id必须核对完整计划和对应行身份。

指纹按依赖顺序形成：原始资料与payload → 提交前ledger清单 → 完整计划 → 当前回执 → 新ledger清单 → 封套外层内容指纹。回执摘要排除entry_sha256自身；封套摘要排除content_sha256自身。生产实现须固定canonical规则和UTF-8/UTF-16检查；本轮没有生产canonical/封套校验API。

**提交前ledger清单引用旧回执，不能包含当前回执或新的封套指纹。** 原始清单仅保存引用，回执原文在archives中只存一次，避免每次把包含全部历史的封套再嵌入回执而递归膨胀。完整闭包仍必须保留，不以“去重”删除来源原文。所有引用应为无环图；缺失、错误角色、环、孤立归档或过深链整体待核/拒绝，不静默丢弃。

这细化了第六十九轮的六份完整来源要求：预览和提交前依旧冻结完整当前封套/来源原文；持久化的历史ledger为**完整清单原文及其全部不可变引用闭包**，不是只存一个摘要。旧只读提案的history_json目前仍不识别此协议，下一轮须经独立新API解析并重算闭包后再设计适配，不能把清单字符串直接传给旧模块冒充已验证历史。

## 消费、引用、重放与删除

消费键为`business_id + bill_id + line_id`，不能包含可变的mapping/component/precision记录ID、目标cost_id、文件名、术语或transaction_id。每批最多50行，来源键与目标分别唯一；一行不得自动拆成多笔，不做跨行合并或比例分摊。既有配对的严格重复/退休检查继续复用。

| 操作或情形 | 拟议行为 |
|---|---|
| CREATE_NEW | 核对完整已消费集合、曾创建/退休目标及当前费用。任何重复或原问题阻断整批，不跳过异常行 |
| REFERENCE_EXISTING | 只读已有费用，新增数0、消费数0；可记录独立引用审计，不能伪装成付款、再次应用或清除已有消费历史 |
| 新事务ID、同一消费键 | 仍为SOURCE_ALREADY_CONSUMED；换mapping、目标、术语不重开来源 |
| 同transaction_id且完整计划/行相符、当前payload等于该回执后payload | ALREADY_RECORDED_NO_WRITE，无新费用或新回执 |
| 同transaction_id但计划/行不同 | TRANSACTION_ID_COLLISION，不能只比较金额或revision |
| 同transaction_id，后续已编辑/删除费用或有后来事务 | RECORDED_HISTORY_REQUIRES_REVIEW，保留历史，不重放、不回退当前数据 |
| 删除已应用费用 | 消费键、曾创建和退休身份保留；删除不撤销回执，也不重新允许应用。反向冲销另行设计 |

每次变更修订递增，revision不得小于回执数+1；ledger有序序号从1连续，回执ID唯一，前链指纹必须相符；未知原点不能被一段看似有效的新回执覆盖。**允许两次事务之间发生明确的人工资料编辑**，前一回执后payload不必等于下一回执前payload；每次仍完整留存自身前后快照并绑定当时有效ledger。不能把合法人工修改误判成账本断链，也不能用其删除消费记录。

G/N/T/X/E/C的受限数值投影、CORE精度、含税/包含、付款/承担、来源/政策回执和未知未来问题沿用[只读提案](fee-application-proposal-validation.md)。有效账本只解释本谱系历史，不把数值兼容或历史未消费提升成业务/税务资格。

## 另存、新业务、分支与恢复

| 情形 | 身份和历史 |
|---|---|
| 重命名、下载重试、工作副本另存 | 保留business/envelope及来源身份、完整历史、回执和退休集合；保存取消不换事务ID |
| 明确复制为独立新业务 | 新business/envelope、账单/行/配对及拟建目标身份；新附件/精度空记录，撤销已知来源确认。原业务历史不改，原资料作为待复核输入，不复制成新业务的已执行回执 |
| 现有费用的引用 | 只作为新业务输入中的既有费用重新核对，不能拿旧CREATE_NEW再次创建。旧业务不因复制重新允许消费 |
| 当前已知完整封套和完全相同候选 | 无变化；仍不自动执行任何费用 |
| 同业务低revision | 旧分支冲突，两份原文保留，不覆盖当前历史 |
| 同revision但内容不同 | 冲突，不能用时间戳、文件mtime或名称判断谁更新 |
| 较高revision但删除旧回执/退休集合、改原点或兄弟分支 | 历史分叉冲突，不自动合并；即使金额相同或新来源互不相交也不能简单合并回执 |
| 较高revision且完整旧历史为前缀、退休集合不减 | 只允许明确预览/采用候选；仍核对完整当前租约、期间修改与来源，不自动覆盖 |
| 首次启动/清缓存后无当前锚点 | 可结构验证并预览，但无法证明这是最新文件。显示PREVIEW_LATEST_UNVERIFIABLE，不声称防住所有回滚 |

保存期间输入变化只标记冻结候选已保存，当前仍未保存。恢复期间的编辑、迟到读取、其他标签缓存变化须阻断覆盖并提供双方原文。缓存读回与SHA不是跨标签CAS锁；不同离线副本继续独立，不能承诺跨设备只应用一次。费用提交协调器、故障恢复和真实浏览器竞态留在后续阶段验收。

## 限额与迁移门槛

拟议UTF-8外层128MiB、归档512条、历史回执64条、单批50行、退休目标3200条、修订1至10亿，逐层深度32/节点300000，归档引用最长32边。既有项目/账单/配对/成分/精度限额分别保持10/5/10/24/64MiB以及原格式各自限制。转义与归档叠加后可能先达到外层上限，不能承诺每个子文件同时达上限仍能保存；这些是待实测的拒绝边界，不是本轮性能或可用性承诺。

达到限额须整体拒绝并保留可备份原文/当前状态，不能截历史、删旧回执、重用序号/ID、滚回revision或用自动压缩隐藏丢失。内部HTML/Excel/PDF各自另定可交付上限，不能把截断报告当成完整备份。客户导出继续只取现有公开白名单，完整封套、历史/身份、内部来源与利润不能透传。

下一轮生产模块须拒绝重复JSON键、坏UTF-16、未知版本/活动字段、伪造内容/引用/回执指纹、环、访问器/原型/符号/稀疏数组/循环和超限。旧项目仅显式采用为UNKNOWN_IMPORTED，不自动升级或激活同名扩展；备份不是正式封套导入。创建、采用、复制、恢复均先产生独立可审查候选，不能隐藏金融写入。

## 本轮验证和下一交付

[固定向量](cases/fee-envelope-design.json)为缩减合成输入，[独立检查器](../tools/check-fee-envelope-design.mjs)覆盖采用、账本、重复/重放、恢复、复制、限额和归档图七类协议。98个有效场景包含应阻断结果，31个非法输入明确拒绝；另15个回执叶字段变更、8组改mapping/目标/事务ID不逃逸消费键，以及2份固定SHA向量。它只核对预先给定的身份/原文/事实，不解析真实新封套、JSON攻击输入、完整来源闭包或应用金额，不验证真实存储、迁移、回滚及客户导出。

[验收记录](fee-envelope-design-validation.md)区分独立设计证据与原3861项真实旧路径回归。下一轮实现**独立只读封套文件模块**：严格格式/闭包、真实来源解析与历史重算、未知历史/旧扩展、完整租约、另存/新业务候选及离线Schema；不直接改费用或接运行工具。随后实现交接/内部审计和恢复控制器，最后才接完整聚合提交协调器。真实手机、真实单据与专业复核按安排暂缓，本轮不新增贸易或税务规则。
