# 来源捕获0.2：按原语义根计数

2026-10-22，第九十轮。开发侧独立原型，尚未替换正式工具的捕获函数。目标是关闭第八十九轮的四个普通JSON反例，保持原保护及业务门槛。

## 问题与选择

[0.1兼容矩阵](cases/fee-source-compatibility.json)中，包装后的帧比原保留数据多两层；默认合成页面多45个节点。这个差值不是所有状态的固定预算。`depth_29`、`depth_30`、`nodes_frame_over`、`nodes_retained_at`在原外层捕获和原保留解析中通过，却被整帧严格复制拒绝。

0.2不提高原严格JSON函数的32深度、300000节点或128 MiB限制。它先显式读取十组生产者，构造与原`retained_json`相同的二十字段根，再调用原严格复制。不会反向解析旧捕获来猜生产者，也不会丢弃未知扩展或合并可变持有者。重复别名仍作为多个语义位置计数。

## 校验顺序与协议

[原型](../tools/fee-source-semantic-budget.ts)按以下顺序工作：

1. 原所有者检查点在每个同步读取前后验证。固定生产者包装和workflow字段先检查自己的数据描述符，拒绝访问器、符号、非枚举属性与自定义原型，之后才使用初始化/忙碌标志。
2. 项目原对象、五控制器、三工作区、未提交控件投影、存储原文和工作流保留值组成原语义根。原严格复制在这个根执行；节点、深度与未知扩展的位置同旧保留数据一致。
3. 不在该树中的账单/配对正文、编辑器、FX行及保留books分别在自己的JSON根执行原严格复制。文件证据独立核对，不推定文件名或保存时间；DOM仍仅保留原投影。
4. 逐字重建原九字段捕获，使用原序列化器、FX选择、阻断顺序及完整捕获128 MiB检查。再运行原保留JSON解析器；外层接收字符串不能代替内层通过。
5. 返回冻结的`INTERNAL_FEE_WORKBENCH_SEMANTIC_CAPTURE`0.2。五个固定元数据字段，加一个已按原根校验的`capture`字段；没有第二份无界数据。重开诊断JSON必须重新检查封闭头部、完整原捕获和内层保留JSON。

协议包装只增加一个对象和五个固定标量节点、一级深度及固定字节开销。它不是把原全局预算改成300006节点或33深度：原财务捕获仍在原根执行原限制，所有正式文件/事务检查保持。物理诊断包装可能比已通过的捕获多这段固定元数据，不能据此导入超限财务数据。外部额外头部、伪造权限、getter或自定义原型均拒绝。

## 不同层次的通过条件

| 观察层 | 表示什么 | 不代表什么 |
|---|---|---|
| 原外层捕获 | 原捕获整体严格JSON/字节检查通过 | 内层字符串有合法内容 |
| 原保留解析 | 原内层深度、节点、字节、重复键等检查通过 | 项目/费用来源、历史或业务资格已满足 |
| 0.2捕获及重建 | 已覆盖场景完整JSON与旧捕获逐字一致 | 所有可能输入等价、可直接提交费用 |
| 原交易与运行候选 | 仍须原来源、编辑、历史、资格、代次及引擎检查 | 诊断JSON自动具有候选或确认资格 |

[比较器](../tools/fee-semantic-budget-diagnostic.ts)分别记录四阶段，只输出固定状态和错误码，不输出业务原文。任何代次变化后停止比较，错误文字中的业务数据不进入记录。调用者提供的同步读取函数属于受信任代码，其自身副作用无法回滚；深层旧对象修改仍须在交互边界调用`touch()`。

## 验证与接入门槛

[本轮验收](fee-semantic-budget-validation.md)保留旧0.1反例与源提交，新0.2记录单列；不重写旧矩阵为成功。普通JSON四例必须完整捕获相同，原超深/超节点、14种不支持JS对象仍拒绝，getter/toJSON执行数为0。复合字节测试通过真实原文、内层JSON及外层JSON，覆盖转义和中文/emoji在原128 MiB前/正好/后一字节。

本轮没有把该原型接入app。下一步先逐项接只读捕获，补齐原预览、候选、确认时重准备、一次提交、失败恢复、客户隔离及完整原生浏览器流程。之后才做同条件1/4/8测量，成功路径、完整备份和恢复都验证前，正式4/8容量仍受限；不从本轮字节兼容推导提速或峰值内存改善。
