## API与来源

`proposeFeeApplication(sources)`接收六个明确槽位：`project_json`、`bill_json`、`pair_json`、`attachment_json`、`precision_json`及`history_json`。前五个必须是真实完整格式的原文；历史允许明确null。严格拒绝额外“已核实”标记、缺槽、getter、循环、非JSON对象、重复JSON键、非法UTF-16、层级/节点/字节超限。沿用严格JSON基础设施，总输入JSON上限64MiB；逐槽上限分别10/5/10/24/64/5MiB，不以这些外层限额扩大旧格式上限。

首个异步操作之前复制输入；真实解析项目、账单、配对、成分和精度文件，验证嵌套原文/内容指纹，重新核对配对、当前项目/账单、边界/人工记录、成分回执和精度政策。五类来源任一格式无效直接拒绝；合法但失配的来源保留完整原文并列出问题。当前项目与原配对分开核对，不静默替换内嵌项目或变更operation。当前提案无法重新计算时明确记录，不返回旧结果冒充当前通过。

`basis`保留六槽完整原文、各槽SHA-256和完整上下文SHA-256；null与任何历史字符串均不同。所有空白、顺序、未选中费用、回执及历史原文变化均改变上下文，不只绑定可见金额。指纹用于变更核对，不是签名、现实订单身份或执行锁。外部项目/账单的仅格式变化不一定使旧配对语义核对失配，但仍改变本提案完整上下文。没有确认/应用接口，指纹不能直接授权写入。

## 数字、待办与引用

每行列出完整映射、原金额/目标金额/已有金额/舍入候选/差额、G/N/T/X/E/C、原币与核算币种、责任/付款/承担方及海关标志。分数以BigInt交叉相乘比较，不使用JS Number或全局Decimal近似判断相等。原金额文本及各原始文件不归一化覆盖。

- 仅原G、原币ROUND候选和新目标amount精确一致、原值不超过6位有效小数、X明确0且E=G、C明确0或完整G时，才可能返回`numeric_projection.status: MODEL_COMPATIBLE`。这是数字表达范围，不代表来源核对通过。
- N/T均未知且明确NO_SEPARATION时仍为null，不写0；不从净额或税额反写成本、利润、退税或抵扣。
- 部分C、非零X/未知经济金额、海关未知/标志冲突、舍入变化、FX及付款/承担方错位分别阻断。G=C=0允许任一明确ADD/EXCLUDE，缺失标志不补默认。
- 全部原提案/边界/回执/政策及人工记录重算结果保留在`reviews`，旧实际付款/经济/海关未认证诊断保留在`preserved_issues`。只有明确列出的五个旧描述诊断不重复算为行级业务阻断；其余未知问题继续阻断。孤立/未匹配的成分或政策也在整份来源问题中保留，不能只挑一个正常行宣称整批通过。
- REFERENCE_EXISTING始终`reference_only:true`、零写入；保留当前已有费用快照，不重新生成或修改费用。CREATE_NEW目标已存在阻断；重复/退休映射及目标首先由真实配对严格解析器拒绝。配对最多50行，成分8行、精度48槽保持旧限额，不隐式截取好行。

输出始终`effect: NO_WRITE`、`financial_writes: 0`，不提供ready、eligible、可执行费用数组、应用函数、回执或事务ID。逐行`blockers`与全局`issues`、原始`reviews`共同阅读，行级空阻断也不表示整批可执行。

## 未建立的历史不能冒充未消费

现有项目/配对格式没有正式`business_id`和应用账本协议。**本轮没有实现真实消费历史核验**，也不把pair_id、文件名、项目名或调用方声明当成业务身份。所有结果明确`BUSINESS_IDENTITY_NOT_ESTABLISHED`、来源消费`NOT_VERIFIED`：

| 历史槽 | 结果 |
|---|---|
| null | HISTORY_NOT_ESTABLISHED，不能理解为从未使用 |
| 合法JSON原文 | 只冻结指纹，HISTORY_FORMAT_UNSUPPORTED；即使声称verified或consumed为空也无效 |
| 非法/重复键/超限JSON | 拒绝输入，不接受伪造的历史证明 |

这项依赖保留到下一阶段正式封套、业务身份与消费键协议；本轮对第六十九轮“已消费键核对”的实现范围作明确收窄，避免在协议尚未建立时创造假证明。真正应用必须有正式账本解析、历史保留/复制/恢复及完整来源消费核对。未知同名旧扩展继续惰性保存。
