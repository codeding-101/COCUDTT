# 恢复后独立业务链路
2026-10-28，第101轮。此实现继续是开发原型，**不替换正式工作台，也不等于完整界面重开**。原费用、风险、税务、汇率与文件格式不变。

## 两套独立状态与新的执行资格
第100轮的只读会话保持原行为。只有经过明确打开的同实例会话，才可创建[新的独立业务副本](../tools/fee-recovery-business.ts)。副本再次建立十组状态持有者，使用现有五类控制器；不从归档复活Promise、旧候选、确认或应用补丁。原会话和原生产页面均保持原数据。

新副本通过既有RuntimeFeeWorkbenchCandidatePreparer准备全部十组字段，并由原引擎重算。新候选、新确认分别使用私有身份；用户检查候选并明确勾选后才能应用。原准备器在点击时重准备、复查当前来源和确认资格，再一次替换新副本的根。重复确认、复制JSON、跨实例、取消、ABA和迟到均不能再次提交。

应用完成后即保留费用、回执与原应用备份；随后显示或文件保存失败不撤销提交，也不能据此重试计费。客户预览与确认在应用后失效，须重新检查。新界面显示核算币种，未知利润仍为null，不补零。

## 有界异步与文件交接
逻辑取消可以先返回，但底层准备未结束时仍占用同一物理工作槽；不因取消而允许请求排队膨胀。交接构建也只有一个工作槽，期间禁止并发准备或应用；取消后迟到结果不得替换当前清单。未提交输入、坏数字缓冲和未读File仍沿用第100轮阻断。

| 文件 | 内容 |
|---|---|
| recovered-project.json | 原项目格式的当前已提交项目 |
| recovered-envelope.json | 原封套1.0及完整来源、账本、归档和新回执 |
| original-recovery.json | 原恢复0.1可解码的完整原恢复数据，保留source_wire与supplement_json逐字原文 |
| new-application-backup.json | 原准备器生成的完整新应用备份，待提交补丁仍只是内部检查资料 |
| internal-handoff-manifest.json | 各文件名称、UTF8字节与SHA-256绑定；无导入或确认资格 |

[恢复文件重建器](../tools/fee-recovery-business-files.ts)保留原捕获时间及两份原文，不通过重新序列化补充对象丢失空白、BOM/CRLF或未知负零。按原48/256/64 MiB界限选择明文或gzip；旧恢复解析器重新解码核对。重建完整恢复数据不承诺原gzip文件的压缩字节逐字相同。原档案、当前项目/封套和新备份分别交付，**五文件清单不是可自动导入的完整新工作台格式**；不能只打开原档案就声称恢复了应用后的新状态。

原128 MiB来源/展开约束、各自节点和深度预算、4/8限制继续保持。没有合并新格式、截断历史或把多个文件的压缩大小当作容量改善。解码完整原档案、生成候选和各文件大小各自检查，不宣称性能或峰值内存改善。

## 客户视图与边界
[独立面板](../tools/fee-recovery-business-panel.ts)不挂载原工作台的全局DOM渲染器。客户输入从空白开始，只调用既有报价白名单与HTML生成器；不继承原客户字段或确认。新的预览与明确核对只能用于当前来源和当前版式，改字段或重新应用会撤销旧资格。固定报价模拟不会被自动改成实际合同报价。

界面分别列内部交接与客户报价，内部文件含成本和历史。下载开始不标记项目或封套已保存；文件保存失败保留当前数据，交接哈希仅检查完整性，不证明业务真实性或专业认证。详见[验证](fee-recovery-business-validation.md)、[原恢复清单](fee-recovery-reopen-design.md)和[下一阶段](development-stages.md)。
