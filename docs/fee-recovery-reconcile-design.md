# 重录后的来源核对与明确同步

2026-10-29，第105轮本地候选。接续[最小交易／报价重录](fee-recovery-trade-validation.md)，使用[原封套来源更新接口](../src/data/fee-envelope.ts)，不更改财税、费用规则或文件格式。依用户决定，第101至105轮继续保留本地候选，不上传档案或更新main／网站。

## 用户流程

1. 在独立业务副本完成交易录入；未提交输入不能进入核对或交接。
2. 五类来源分别显示是否变化和完整原文字节数。初步提示尚未重新验证封套，也没有执行资格；所有变更来源须明确选择，保持来源不能顺带选成“已核对变更”。
3. 完整准备解析原封套和当前五来源，调用原updateFeeEnvelopeSources、serializeFeeEnvelope及reviewFeeEnvelope。候选显示前后SHA-256、修订号、原回执及退休编号数量，以及同步后仍存在的待办。
4. 勾选“已核对变更来源与未解决事项”，再明确同步。确认阶段按当前上下文重新准备原候选，经过完整捕获预检后一次安装；复制的JSON、旧候选或只准备未确认都不能安装。

来源同步只改变封套当前快照。它不会重绑配对、成分或精度，不会清除失配待办、应用费用、补齐缺失事实或批准客户报价。历史应用时的项目与当前交易不同是明确记录的状态，不通过改写旧回执来消除。

## 原子更新与捕获边界

[独立核对模块](../tools/fee-recovery-reconcile.ts)通过[业务会话](../tools/fee-recovery-business.ts)访问本会话的真实十组持有者。候选绑定所有者检查点、私有对象身份和当前代次；相同文字的A→B→A也不会恢复旧资格。

安装前用原语义捕获0.2规则检查精确的预期投影，包括新封套、更新前封套、控制器epoch／read_token、显示工作区generation及客户核对失效。已验证的真实安装后捕获与预检逐字一致；不拿一个小型差异列表替代完整捕获预算。

一次根替换只涉及封套控制器、封套工作区及workflow三个参与者。项目、原利润／买方结果、费用、回执、原归档及应用备份保持；当前来源必须与已提交持有者一致。旧费用候选和客户核对失效，当前封套的旧文件证据仍是旧文件证据，内存同步不等于另存成功。

## 取消、失败与记录

准备和最终确认共用一个物理工作槽。取消及时撤销逻辑资格，但不冒称停止底层摘要计算；迟到任务结束前拒绝重入，不排队。输入变更、业务上下文变化、外部取消或关闭均撤销旧候选。确认开始时消费私有候选，失败后须重新准备。

解析、核对、原文完整性、捕获预检和更新记录预算都在根替换之前。失败保留当前已提交交易、封套及旧记录；显示失败发生在更新之后时，已完成更新和记录继续保留，不回滚或重复同步。

每次成功同步保留完整更新前／后封套、来源指纹与未解决事项。记录不具备回放、费用或客户批准权限。本独立容器暂限64条及序列化后64 MiB UTF-8，超限整次拒绝，不截断旧记录；这不是峰值内存、业务金额上限或原恢复格式预算的变更。原128／256／48／64 MiB预算及4／8笔限制保持。

## 界面及交接范围

[核对面板](../tools/fee-recovery-reconcile-panel.ts)只操作自己的容器。测试容器明确连接最小交易面板，只有实际输入状态改变时才刷新核对，单纯失焦不重建勾选框。另修正原型表单标签：实际报价只读字段称作“当前术语实际报价金额”，固定报价和目标比较分别称呼；没有改变报价取值或计算。

当前原handoff可得到匹配的项目／封套数据，并继续保留原恢复档案及本会话新应用备份。**本轮没有新的整套更新记录交接文件或真实下载验收，也没有把这组文件变成可自动完整重开的格式。**所有来源更新记录目前只在该独立会话内存中；正式交接／恢复入口未开放，不能靠刷新页面保全它们。

下一阶段先设计包含全部来源更新记录的内部交接，核对当前项目／封套、原恢复档案及应用备份，验证真实下载、取消、失败和重新打开的权限边界，再扩展完整表单与原工作台切换。详见[验收](fee-recovery-reconcile-validation.md)、[测试](../tests/fee-recovery-reconcile.test.ts)和[开发阶段](development-stages.md)。
