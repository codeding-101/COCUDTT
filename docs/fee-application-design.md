## 先核对现有模型能表达什么

[实际边界测试](../tests/fee-application-foundations.test.ts)通过现有函数核对如下事实，不新增法规结论：

| 路径 | 当前实现 | 对应用设计的约束 |
|---|---|---|
| [CostItem](../src/domain/cost-item.ts)、[汇总](../src/engine/aggregate.ts) | 单一amount经商业换算后参与卖方成本或买方额外费用；服务费没有独立抵扣台账 | G、N、T、X、E不能任意替换amount。G=113、X=13、E=100时，单写113或100都不能同时表达应付和经济成本 |
| [海关组成金额](../src/engine/tax/dutiable-value.ts) | 中国模式ADD按费用完整原币金额加计，EXCLUDE排除；不是任意C金额字段 | G=113、C=40不能靠ADD/EXCLUDE表达；不得通过“扣除13税额”或修改商业金额间接实现 |
| [只读核对](../src/engine/container-cost-review.ts) | 含税/税率引用、经济成本、海关成分和实际付款仍有独立待办 | 成分算得出、政策已记录不清除原待办，也不证明付款、抵扣或归类资格 |
| [费用归属汇总](../src/engine/aggregate.ts) | 按责任决策汇总；payment_party/economic_bearer不是收付清偿台账 | 付款人与承担方不同的垫付、偿还、代付首版应用不支持；不能把付款方当成成本承担方 |
| [原提案](../src/engine/container-cost-proposal.ts) | 保留完整原金额，超过6位核心精度仍阻断；新建目标在项目内存在时提示冲突 | 精度政策不能消除CORE_PRECISION_LOSS。插入费用后原CREATE_NEW提案不能继续冒充当前可重复执行动作 |

这里的G是应付金额假设，不是“已实际付款”；E是本成分G−X的费用净额，不是经营利润；C是另行记录的海关组成金额假设，不是税款或完整完税价格。

## 拟议首版：受限投影，不替旧模型补造字段

独立提案模块首先返回字段映射差异、阻断项、保留待办和来源依据。缩减检查器的`UNCHANGED_ORIGINAL_CASH`只说明数字能投影到旧单金额模型，**不是ready、apply或业务资格**。

| 成分/政策 | 拟议处理 |
|---|---|
| 原G、原币舍入候选、目标amount完全数学等值，且原G可精确表达为不超过6位小数 | 只保留原币原金额投影；原文本、币种、目标、合同及FX字段不静默归一化 |
| E已知且E=G，X明确为0 | 单金额模型在本成分上没有遗漏独立抵扣调整；仍须全部真实来源、合同及上游核对，不能据等式认定资格 |
| C明确为0或原G | 数字上可分别对应EXCLUDE或完整ADD；实际是否加计仍由来源/口径核对，不从Incoterm、付款方或报价包含推断 |
| N/T | 不直接写amount、利润、采购成本、退税或进口增值税抵扣。两者都未知的明确不拆分假设不能被填零；一方未知、另一方已知不得冒充完整拆分 |
| E≠G、X非零、经济金额未知 | `SEPARATE_ECONOMIC_MODEL_REQUIRED`或未知待办；先扩展能分别表达应付/经济口径的模型，再研究应用 |
| 部分C或C未知 | `PARTIAL_CUSTOMS_MODEL_REQUIRED`或未知待办；不能用整个G的ADD替代，也不拆出一笔无依据“海关调整费” |
| 舍入差额非零，或原金额超过核心精度 | 保留候选/原值/正负差额并阻断；不能用候选取代原账单再宣称匹配 |
| FX政策、目标币种变化 | 首版不应用。不能把换汇候选写回原币amount、把反向汇率写fx_rate或重复换算；海关诊断尤其不得改商业费用或税款 |
| REFERENCE_EXISTING | 保持只读引用，新增费用数为0；不能重新创建、更新amount或改归属。未来账本可记录引用行为，不能伪装成再次付款或费用写入 |

既有提案、原始金额、来源、含税/税率、包含关系、派生/货值目标、重叠和未知未来问题默认保留。首版不设置“忽略所有待办”按钮；缩减向量中的`issues`代表应由未来生产模块从真实完整来源重算的阻断项，`diagnostics`仍原样保留。它们不是可由导入JSON自行声明通过的可信证明。旧只读报告中的实际付款/经济/海关诊断不被本模块改成已认证状态。

## 完整上下文与明确确认

冻结依据覆盖六份完整原文：当前项目、账单、配对、已提交成分附件、已提交精度文件及应用历史账本。完整原文与重新计算的指纹同时保留；不能只绑定文件名、revision、记录ID、显示金额或被选中的一行。来源中的空白/键序、未选中费用、汇率、日期、依据、回执、历史及账本变更均使待执行确认失效。未知扩展不得在重算时丢失或激活。

未来生产前置核验必须解析真实格式、重算嵌套指纹和关联、验证完整目标/币种/通道/原值及当前回执；检查器中的六份缩减字符串没有这些能力。任一配对/核对/成分/精度编辑未提交、当前计算待更新或来源不一致时阻断应用。预览到确认期间绑定完整计划、上下文、当前内存代次和一次性令牌；暂存/序列化结束后、提交前再次核对。不同标签或迟到读取不能自动覆盖新输入。

确认只授权冻结的整个批次。首版最多研究50行且逐行有稳定目标，任一行缺条件、重复或有阻断，整批不提交；不“跳过坏行”造成用户误以为全部已应用。

## 防重复与稳定身份

在一个有效文件谱系内，消费键为`business_id + bill_id + line_id`。mapping/component/precision记录ID、术语、文件名、报价币种、目标cost_id或transaction_id变化不能让同一来源重新变成未使用。首版一行账单不拆为多项费用，不跨行合并或按箱/日/运输段自动分摊。

- 同批同来源键或同目标ID阻断。CREATE_NEW目标已存在或已退休时阻断，不凭名称/金额猜为同一条；REFERENCE_EXISTING目标必须存在。
- 事务预览首次冻结时建立transaction_id，保存/下载取消、失败、刷新或渲染不能自动换ID再应用。相同ID但不同完整计划为冲突。
- 完整回执与请求计划相符且当前财务payload仍相符：`ALREADY_RECORDED_NO_WRITE`。后续业务已改变：`RECORDED_HISTORY_REQUIRES_REVIEW`，保留历史且不重放、不回退新项目。新ID仍须通过已消费来源检查。
- 删除项目费用不能删除消费历史或复用退休身份；反向撤销须将来单独设计显式事务，首版不自动重开来源。
- 明确新业务须重建业务及相关来源身份并清除旧确认，不能改项目名称就清空账本。丢失账本时不从现有费用猜造回执，更不能自动建立“全未使用”历史。

回执拟记录事务ID、完整计划指纹、来源/目标、前状态指纹和后财务payload指纹。后payload指纹不包含回执自身，外层内容指纹最后计算，避免自引用摘要。真实格式、历史保留和资源上限尚待文件阶段定义。

这不是跨文件/跨设备全局“只执行一次”。独立离线副本、用户编辑后重新计算指纹和缺失历史无法靠SHA证明现实订单唯一；SHA用于变更核对，不是签名或业务真实性认证。

## 包含、重叠和费用承担

复用并重算原提案、只读覆盖、父子包含、报价声明、替代组与当前术语筛选。缩减覆盖向量只讨论显式箱号和两端计入的日期区间：不同scope标签、币种和联合/分开D&D名称不消除交集候选。无交集只说明这个缩减范围未相交，不能证明没有报价包含或重复收费；箱号/日期缺失仍未知。

报价已含不等于海关排除。费用归属、付款方、承担方、发生原因和实际履约来源分别核对；不能按术语、费用名字或“由谁录入”补造默认值。CIF/CIP的风险转移、保险以及其他原贸易逻辑保持，本轮不定义新解释。

## 事务提交与故障边界

未来运行态应由一个协调器持有完整不可分的应用状态：项目/账单、历史配对/附件/政策、应用账本、文件状态和未提交输入。先在私有副本构建、验证全部引用/ID/版本、重新计算、形成差异并完整序列化；提交前再核对完整依据；**一次替换聚合状态**，不得逐个调用旧控制器setter形成半新半旧状态。

| 阶段 | 失败处理 |
|---|---|
| 项目、账单、配对、附件、政策、账本暂存；验证、重算、序列化；提交前检查 | 原聚合状态逐字保持，新增费用/回执均0；待执行候选和原文供备份，不覆盖新输入 |
| 已观察到本机草稿冲突 | 提交前阻断，不覆盖其他位置原文 |
| 完整状态提交 | 该批全部费用与一份事务回执一起可见；REFERENCE_ONLY不新增费用 |
| 提交后缓存写失败 | `APPLIED_MEMORY_ONLY`；保留新状态和账本，提示待备份，不能显示“未应用”诱发再次应用 |
| 写后读回被其他位置替换或不可核实 | `APPLIED_CACHE_CONFLICT`；保留内存及可取得的双方原文，不盲写旧缓存或声称已持久化 |
| 提交后渲染失败 | `APPLIED_RENDER_FAILED`；恢复界面备份包含新聚合状态/账本，不能悄悄财务回滚或再次插入 |
| 文件保存失败/取消 | `APPLIED_FILE_NOT_SAVED`；应用与文件落盘分开，重试保存冻结快照，不重试费用应用 |

整批失败回滚承诺仅限提交前。提交后的自动缓存、文件写入与界面是独立副作用，不能声称浏览器内存、localStorage和磁盘形成跨资源原子事务；原文比较/读回也不是跨标签CAS锁。应用账本须和财务状态放在同一完整持久化封套，不能用两个独立草稿槽位冒充持久化原子性。

## 原配对与文件格式

已应用费用与原CREATE_NEW来源会发生角色变化。原配对/成分/精度文件须完整作为历史保留，相对新项目明确失配；不能把内嵌项目偷偷替换为新项目并继承旧回执。若继续建立“当前配对”，必须显式新修订、退休旧CREATE_NEW映射、建立REFERENCE_EXISTING映射，并使所有受影响的成分/政策重新绑定和复核；不能为了通过旧校验静默改operation或删除来源。

项目0.8/0.9、配对1.0/1.1、成分1.0、精度1.0及内存备份当前均没有应用契约。未来须以明确新封套/格式采用和迁移保存；旧项目中的同名扩展保持惰性，恢复备份不当作交易/应用文件导入。不在本轮增加Schema、版本常量、迁移函数或打开按钮。
