# 费用税务成分与未知值：实现前设计

2026-10-17，第五十七轮。交付设计、独立手算和拒绝案例，**不启用运行功能、不改变旧金额、不新增项目/配对字段**。下一轮先实现独立只读模块；通过结构、精确算术、旧扩展保护及完整回归后，才另行设计文件和界面接入。精度选择及费用原子应用仍在后续阶段。

## 现状与依据

现有[费用类型](../src/domain/cost-item.ts)记录`tax_included`和`tax_rate_ref`，但不具备服务发票价税分离/抵扣语义。[只读核对](../src/engine/container-cost-review.ts)保留原币原值、税务/精度待办，经济成本和海关调整为`null`；[核对计划](../src/domain/container-cost-review-plan.ts)的`KEEP_RECORDED_AMOUNT`也不能清除这些待办。本轮不改变这些行为，不借旧字段激活新算法。

2026-10-17重新读取下列官方文本的相关条文。只用于确定模型边界，不代表查尽后续公告、所有交易例外或完成专业复核：

| 来源与条文 | 本设计采用的边界 |
|---|---|
| [财政部公布的《关税法》](https://www.mof.gov.cn/jrttts/202404/t20240429_3933790.htm)，第二十四至二十六条 | 运保费用与起卸前后范围、单独列明的费用/税收须分别核对；不能根据费用名称、费用承担方或抵扣金额自动给出海关成分 |
| [税务机关公布的《增值税法》](https://shanghai.chinatax.gov.cn/zcfw/zcfgk/zzs/202412/t474694.html)，第七、十四、十六、二十二条 | 价外税、进口组成计税价格、扣税凭证及不得抵扣情形分别处理。算出税额不是取得抵扣资格；服务发票税额不能再作为同一笔进口VAT扣除 |
| [《增值税法实施条例》](https://shanghai.chinatax.gov.cn/zcfw/zcfgk/zzs/202601/t478908.html)，第十一、十二、十六条 | 合并定价换算与凭证列明税额是不同输入依据；拆税比例不认证凭证税额、资格或适用税率，不套用运输/THC通用税率 |

以下金额仅为给定数字的合成假设，均非实际税务认定。零税率算式不代表免税、零税率待遇或不征税资格。`ADD_COMPONENT=113`等案例只检验独立字段传递，不能证明该金额依法可加计。

## 四个概念与三条通道

| 通道/金额 | 含义 | 不能据此推断 |
|---|---|---|
| `cash`（G） | 原币账单应付总额；已知可为0，未知为null | 不证明实际已付、谁承担、净额结算、信用证费用或偿还安排 |
| `net`（N）与`tax`（T） | 已给出的价税成分，或给定比例的精确算式 | 不证明税种/税率/征收率合法、凭证税额或资格有效 |
| `credit`（X）与`economic`（E） | 本次明确抵扣金额假设及`E=G−X`的费用净额口径 | 不是已抵扣、已退税、会计确认、现金流或完整经营利润 |
| `customs`（C） | 同币种账单中明确单列、拟额外加计的成分 | 不是完整完税价格、税额或已批准申报；不从商品价倒扣，也不因报价内含或抵扣而自动变更 |

三条独立通道是应付G、费用净额假设E、海关加计C；N/T/X提供审计链。举例：G=113，N=100，T=13，X未知，则E未知；本次明确不作抵扣调整时X=0、E=113；在有明确金额及凭证/资格假设的输入下X=13、E=100。C仍单独填写依据，可以未知；不能从E=100直接填C=100。

所有已知数字都只在合成假设下有效。首版没有`ready`、`apply`、`confirm`或“可入成本”标志，即使六项均有数字也不能自动替换原成本、解除提案待办或进入确定推荐。

## 首版独立输入契约（拟议0.1，尚未是有效文件格式）

单笔只处理一条服务费假设，同一币种，无退款、红字、代缴、混合税种或混合税率。严格字段白名单；不直接接收旧CostItem、账单行或衍生进口税行。需要后续独立转换设计，而非把`tax_included=true`或`tax_rate_ref=VAT13`转成新事实。

```text
line_id: 1..80 ASCII标识，仅在当前假设集合内区分行
currency: 三位大写币种；不根据币种推断小数位或税制
gross: 非负十进制字符串 | null
tax:
  UNKNOWN
  NO_SEPARATION
  EXPLICIT { net, tax }
  GROSS_RATE { rate }
credit:
  UNKNOWN
  NONE { basis }
  ASSUMED { amount, basis, document_ref, eligibility_ref }
customs:
  UNKNOWN
  NOT_ADDED { basis }
  ADD_COMPONENT { amount, basis }
```

每个分支由`kind`区分，只接受本分支字段。金额最多24位整数、18位小数，不接收Number、指数、空串、负数或逗号；null只用于显式允许的未知应付额。参考文字须非空且不超过200字符。参考标识只是人工输入，不是查验发票、身份或原产地的认证。

- `UNKNOWN`表示未知，不补0。`NO_SEPARATION`表示本次不分离，N/T仍未知；不是宣告无税。
- `EXPLICIT`要求已知G、N/T非负且**N+T严格等于G**。不以0.01容差吞掉差额，也不反推缺失G。
- `GROSS_RATE`要求已知G和显式比例r，精确算`N=G/(1+r)`、`T=G−N`。首版工程边界为`0≤r<1`，并非所有税种的法定上限；不得缺省选13%、9%或6%。
- `NONE`只表示本次明确不作抵扣调整，X=0，有说明；不是认定依法不得抵扣。`ASSUMED`须给金额和三项说明/凭证/资格引用，且已知T、`0≤X≤T`；部分抵扣必须明确金额，不由比例或纳税人名称自动产生。
- `NOT_ADDED`在有说明下C=0，表示本通道不额外加计；不等于从已含金额中扣减。`ADD_COMPONENT`须已知G、独立金额与说明，首版只接受`0≤C≤G`的同币种账单子集；跨币折算、价外调整和其他海关估价另设范围，不自动截断。
- 已列明N/T与未舍入的比例算式可以不同，例如G=1，凭证假设N=0.88、T=0.12；比例13%的精确算式为100/113和13/113。两种输入模式不可同时激活或相互覆盖。差额与舍入政策后续单独设计，不据此认证任何一方。

## 精确输出与未知传播

设计检验器使用约分后的非负分数`{numerator,denominator}`，分母正且分子/分母均为整数字符串。`1÷1.13=100/113`不截成6位或2位，不向全局Decimal设置注入新精度。未来模块的内部表示与展示需独立审查，不把此设计输出当当前可导入JSON。

| 输入缺口 | 保留的输出 |
|---|---|
| G未知 | G未知；不能从成分凑出G，带已知拆分或加计的输入拒绝；明确X=0仍不使E变为0 |
| N/T未知但本次明确X=0 | N/T未知；若G已知则E=G，说明这是本次不作调整，不是自动认定不存在税 |
| X未知 | X/E未知；即使G为0也不自动替用户确认抵扣决策 |
| C未知 | 仅C未知，不能用E、N、G或已含报价旗补齐；不拖掉独立已知的G/N/T/X/E |
| 已知C=0 | 仅代表独立通道明确不加计；不能改变未知X/E或原商品税基 |

按币种汇总最多8个不同line_id，混币/重复ID/空集/超限整体拒绝。每列分别输出`totals`、`known_subtotals`和`unknown_counts`：任一行该列未知，完整合计就是null，同时保留已知部分小计与缺口数量。无已知值的小计0也不能被呈现成完整总额；必须显示未知计数。重复ID拒绝仅防当前集合明显重复，不证明不同编号没有重复发票或税款。

## 与旧模型的隔离及后续门槛

1. 本轮只有[固定手算/反例](cases/fee-tax-components-design.json)与[独立检验器](../tools/check-fee-tax-components-design.mjs)，生产源码无导入；80文件2678项应用回归、旧引擎和文件格式保持。本设计不清除只读核对原待办。
2. 下一轮实现独立只读函数/验证器，证明冻结输入、精确分数、未知合计、限额及随机独立对照；仍无界面、业务文件字段、税额确认或费用应用。EXAMPLE/未核对/已确认后变化的绑定另行设计，引用文字本身不变成确认。
3. 文件/界面接入须显式新版本、完整项目/配对/账单/术语/行/币种/成分/凭证与资格快照绑定；任一变更撤销接受。旧同名扩展不得激活或覆盖，业务复制撤销旧确认；客户文件继续白名单。
4. 导入旧衍生进口VAT、代缴税及父项包含前，必须独立设计凭证身份、范围和重复抵扣/计入检测；缺资料继续未知。不得凭现有`USER_CONFIRMED`或任意凭证编号消除全部待办。
5. 精度选择、逐行/汇总舍入、汇率、人民币计税组成至分和税款舍入分别验收；最后才设计费用映射、幂等、完整重验证和原子应用。任何阶段都不能把设计算术当作税务专业意见。

真实手机、实际单据和人工专业复核按用户安排仍暂缓。当前验证详见[本轮验收](fee-tax-components-design-validation.md)；能力边界仍以[矩阵](capability-evidence-matrix.md)为准。
