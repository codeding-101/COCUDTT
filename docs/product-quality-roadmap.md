## 第一轮已实现：保护业务数据

| 已核实缺陷 | 修复后的行为 | 回归验证 |
|---|---|---|
| 文件解析只检查顶层字段存在，未检查 goods、fx_books、税务规则等嵌套结构 | 检查所有已知结构与枚举，提示字段位置；不静默改写未知扩展字段 | 项目文件的嵌套损坏、三种比较基准、费用依赖与阶梯档位测试 |
| 打开文件先替换项目，再准备汇率行，准备失败可能留下半更新状态 | 全部准备成功后才替换当前项目；失败保留旧内容、结果和草稿 | 实际界面事件处理的回归测试 |
| 打开失败后重算覆盖错误提示 | 失败立即显示错误，不再重算旧项目覆盖提示 | 坏文件、文件读取失败测试 |
| 保存取消和写盘失败都退回下载并清除未保存标记 | 取消或失败明确提示；成功写盘后才更新保存状态 | 取消、磁盘写入失败测试 |
| 文件名与错误详情未经转义直接插入 HTML | 状态以纯文本显示，增加状态区域的辅助技术语义 | 文件名与版本字段中的 HTML 注入用例 |
| 草稿汇率行未经校验，恢复失败后启动重算会覆盖原草稿 | 校验汇率行；恢复失败时保留原存储并显示说明 | 损坏草稿与未完成输入恢复测试 |
| 本地草稿写入失败被静默忽略 | 显示自动草稿保存失败，提醒保存项目文件 | 浏览器存储不可用测试 |
| 示例报价对象复用，编辑当前报价会污染以后载入的示例 | 每次生成独立的报价与比较基准对象 | 两次载入示例的隔离测试 |

结构校验与业务数值校验分开：空金额和未完成汇率行仍可存档恢复，能否计算由引擎判断。文件能打开不代表税率、合同或数值已经通过业务核实。

文件操作测试使用最小 DOM 替身执行真实事件处理与渲染函数，验证状态和数据；它们不验证布局、浏览器权限或实际下载完成情况。损坏草稿只在启动时受保护，继续编辑或打开其他项目会更新草稿，提示中已明确这一点。

第二轮全套368项测试通过，静态审查与类型检查通过，已构建单文件网页。真实Edge验证了离线运行、日期纠正后的恢复、坏文件保留草稿和结果，以及1440px桌面、390px与320px手机视口无横向溢出。规则依据、对照算式与未覆盖业务见 [中国进口规则与验收](china-import-validation.md)。

### 第三轮进展：来源追溯与排名条件

已完成税率、HS条目、汇率与费用项显式汇率的来源、适用期、核对日期及人工状态记录；结果展示实际来源。已核对的数据或来源修改后须重新确认，导入时也检查数值快照。示例与未核对来源仍可测算，但在中国模式下不能参与排名；非零待确认/未拆分费用、不完整税基及严重错误也会排除受影响方案。容器格式升级至0.3，兼容读取0.1和0.2。

第三轮397项测试通过，并修复真实浏览器发现的离线打包替换令牌错误；构建会检查最终脚本语法。Edge验证了来源编辑、排名恢复及撤销、文件数据往返、过期汇率和坏文件处理，桌面及窄屏无横向溢出。详细分析与检查边界见 [来源与排名验收计划](source-readiness-validation.md)。

### 第四轮进展：贸易路线与业务条件

已增加出口国/地区、进口国/地区、原产国/地区与申报制度；原产地及关税待遇独立核对，协定需记录名称；开启VAT抵扣需身份、用途与资料核对。条件修改后的资格确认失效，范围不匹配或未核对的方案退出排名。格式升级到0.4，旧文件不自动填入资格。

### P0：确定国家、税务规则和输入来源

现有默认配置是中国海关模型，`tests/fixtures/virtual-trade.ts` 的德国出口样例使用虚拟税率。该样例验证计算链，不能证明德国进口税费准确。第四轮已增加出口国、进口国和原产国字段，但这不等于自动判定资格或支持相应国家税制。

建议先完整支持一个经过核实的贸易路线，然后扩展国家，而不是仅修改税率来声称支持全球贸易。

验收要求：

1. 项目记录出口国、进口国、原产国和税务规则档。规则档的适用范围始终可见，不匹配时阻止正式测算。
2. 税率、汇率记录来源链接、适用日期和核对日期；示例数据明确标记，过期或未经核实的来源提示核对。（第三轮已完成记录、提示及排名检查；尚未自动核验来源内容。）
3. 核对从量税单位、VAT 抵扣资格、贸易协定适用条件与退税主体。不能凭 HS 编码自动推定协定优惠或抵扣资格。
4. 整理至少三笔匿名业务案例，分别人工核算利润、买方支付、税基与税额。输入、公式、来源、预期数值、精度要求一并归档；金额差异应能解释到舍入或实际费用。

### P0：说明方案比較的成立条件

只有货值、实际启用费用、估价调整和税务事实相同时，比较税基与税额才保持一致。第六轮已按方案启用费用并重算税额，运价变化可以造成税额差异；不能把税额一致写成所有交易的普遍结论。

第六轮已支持费用适用术语和互斥替代组，分别录入同一运段的两种运价。当前仍共享合同报价，下一步支持各方案独立合同报价及有效期。费用归属不自动证明实际组织方。

验收要求：

1. 比较表显著说明固定了哪些事实、允许哪些量变化，并解释固定报价和固定买方总支付回答的不同问题。
2. 将方案是否可计算、是否存在待确认费用、是否满足当前排名检查分别表达。第三轮保留 `feasible` 表示运输术语可用且报价求解收敛，增加 `decision_ready` 和排除原因；排名同时检查两者。它不代表完整业务资格已经得到核实。
3. 接入已有 `conditionalSensitivity`，展示待确认费用分别由双方承担时的影响，避免把不完整成本汇总当成确定结论。
4. 为方案提供费用启用条件或方案专属金额，使用一笔卖方运价与买方运价不同的案例证明没有重复计费。

### P0：把专业规则与依据连起来

责任与风险已经分开建模，这是可保留的基础。下一步建立“规则 → 官方依据 → 适用条件 → 例外 → 测试用例”的追溯表。

首批规则应覆盖 CIF 与 CIP 的默认保险范围差异、C 类术语的费用终点与风险转移点、FCA 的交货地点分支，以及合同约定覆盖标准术语的处理。保费金额的存在不能证明实际保单满足保障范围与保额要求。

已查阅的基础来源：

- [ICC：CIF 与 CIP 的差异](https://academy.iccwbo.org/incoterms/article/incoterms-2020-cip-or-cif/)：运输方式、交货与保险范围。
- [ICC：CPT 与 CIP](https://academy.iccwbo.org/incoterms/article/incoterms-2020-cpt-or-cip/)：CIP 的保险义务与至少 110% 合同价值的保额要求。
- [ICC：C 类与 D 类的风险转移](https://academy.iccwbo.org/incoterms/article/incoterms-2020-c-or-d-rules/)：支付运输费用至目的地不等于承担全程货损风险。

这些资料用于建立产品规则追溯，不代表现有全部税务与术语实现已获外部审核。

## 再下一阶段：完成一条业务工作流

以“业务员收到询价 → 录入交易 → 核对费用及来源 → 比较三个候选方案 → 导出内部测算报告”为首条完整工作流。

| 优先级 | 交付物 | 验收方式 |
|---|---|---|
| P1 | 空白交易入口、引导式首笔录入、示例标识 | 请 3–5 位目标用户完成同一任务，记录完成率、耗时与误填位置；人数与指标是计划，尚非已取得成果 |
| P1 | 内部测算报告导出 | 报告包含输入快照、币种、公式口径、来源日期、方案比较和待确认事项；报告金额与项目逐项一致 |
| P1 | 浏览器回归与跨设备验收 | 覆盖 Chrome/Edge 桌面、手机布局、file:// 离线运行、文件打开、取消保存、存储禁用和恢复草稿 |
| P1 | CI 与可复现发布 | 每个 PR 运行单测、静态审查、类型检查和单文件构建；发布能对应源码提交与验证结果 |
| P2 | 历史方案和汇率、运费敏感性分析 | 调整一个变量时能追溯结果变化；历史快照不被当前编辑覆盖 |
| P2 | 批量录入 | 先预览和逐行校验币种、单位与金额，再允许写入；错误行不会悄悄成为零金额 |

## 简历与面试证据
