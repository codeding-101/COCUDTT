## 1. 产品形态与技术形态

### 1.1 形态结论

**纯静态、本地优先的网页应用。无服务器、无登录、无账号。**

- 数据不离开用户机器。项目文件由用户显式保存到自己选择的目录。
- 分发形态两种：
  - **静态目录**（多文件）：开发与自用，需要 `file://` 之外的方式打开（见 1.3）
  - **单文件 HTML**（构建时内联全部 JS/CSS）：用于发给别人查看结果
- 不做桌面应用。只有当出现「批量扫描目录」「与财务/报关系统文件级对接」「无人值守批处理」时才考虑套 Tauri 外壳。

### 1.2 工程栈

| 项 | 选型 | 说明 |
|---|---|---|
| 构建 | Vite | 开发用 dev server，产物为静态文件 |
| 语言 | TypeScript（strict） | 领域模型用类型表达，禁止 `any` 进入 engine 层 |
| 测试 | Vitest | engine 层纯函数，全部可单测 |
| UI | 无框架 / 极轻 | 录入表格 + 结果表两张核心界面 |
| 数值 | 定点十进制 | 见 1.4，禁用浮点参与金额运算 |
| 持久化 | IndexedDB + 项目文件 | 见第 12 节 |

### 1.3 `file://` 的约束

浏览器用 `file://` 打开页面时，ES 模块会被 CORS 拦截。因此：

- 开发与自用：Vite dev server 或任意静态文件服务器
- 对外汇报：构建单文件 HTML（全部内联），可双击打开

**约束：项目文件是数据的唯一权威来源（source of truth），浏览器存储只做自动草稿的便利层。** 原因见 12.2。

### 1.4 数值精度

- 所有金额、汇率、百分比使用定点十进制，序列化为字符串。
- 中间计算保留 6 位小数，展示保留 2 位，汇总时统一舍入。
- 舍入方式固定为 `ROUND_HALF_UP`，并在结果中标注舍入发生的位置。
- 汇率换算方向固定：`base_amount = original_amount × fx_rate`，其中 `fx_rate` 定义为「1 单位原始币种 = ? 单位核算币种」。文档与 UI 均按此口径展示，避免方向歧义。

### 1.5 范围界定（核心 / 次要）

核心需求：**同一商品、同一数量、出口到同一目的地市场，比较不同贸易术语下的成本与利润。** 据此划分：

| 模块 | 定位 |
|---|---|
| 11 术语横向对比 + 比较基准（第 11 节） | **核心** |
| 费用自定义（任意名称、任意计费方式） | **核心**：不得因系统不认识费用名称而无法计算 |
| Cost Engine / FX Engine / 责任判定 / Risk Engine | **核心**：对比结论的正确性依赖它们 |
| Tax Engine | **核心但可简化**：DDP、DPU 下关税与增值税是卖方成本，算不准则对比失准；v1 允许按商品大类手工给定税率，不建 HS 编码库 |
| 出口退税（Export VAT Rebate，见 9.5） | **核心**：中国出口商利润的主要来源之一，必须计入利润模型，不能只作备注 |
| 方案层（Scenario） | **核心**：对比功能的实现基础 |
| 项目文件保存与重新打开 | 必要的最低限度持久化 |
| 导入导出、历史归档、报表美化、图表、多设备同步 | 次要，可后置或不做 |

UI 只承担两件事：录入商品与费用、展示对比表。

### 1.5.1 布局决策：铺满宽度，只上下滑动

界面不许出现横向滚动。这不是审美偏好，是可用性硬约束：横向滚动会让用户看不见右侧内容、找不到自己在哪一行、并且**必须同时操作两个滚动轴**。

要做到这一点，必须改数据排布方式而不是调 CSS：

| 表格 | 横滚的原因 | 改法 |
|---|---|---|
| 11 术语对比 | 11 个术语横排 = 12 列 | **转置**：术语成为行（11 行），指标成为列（8 列）。术语名短、指标列可压缩；更关键的是——**行是廉价的轴（纵向滚动免费），列是昂贵的轴** |
| 费用项录入 | 11 列字段表格 | 改为**卡片**：头部一行放名称、核算金额、归属标签、删除；字段行用 flex 自动换行，宽度不够就换行而不是横滚 |
| 逐项明细 | 原币/核算金额各占一列 | 合并为一格：核算金额为主，原币金额小字在下 |
| 汇率 | 7 列表格 | 每本汇率一行，字段用 flex 换行 |

**次要值下沉到小字**，把 10 个指标压进 8 列：卖方利润格内小字标"不含退税"、买方总支付格内小字标"不含可抵扣税"、报价外费用格内小字标"其中进口税费"、承担范围格内小字标"待确认/告警数"。单元格变高是免费的（纵向），变宽是昂贵的。

**窄屏降级**：≤760px 时对比表与明细表用 `data-label` 属性转成堆叠卡片（一行一个术语/一笔费用，字段名在左、值在右），同样不需要横滚。

实测（1440 / 1024 / 820 / 700 / 420 五档）：**页面与任何容器都没有横向溢出**，`overflow-x` 探测结果为零。

### 1.5.1.1 底部留白：为任务栏留冗余

页面底部必须留出大于系统任务栏高度的空白，否则滚到最底部时最后一块内容被任务栏遮挡。

网页拿不到任务栏高度，它随显示缩放变化：Windows 100% 为 48px、125% 为 60px、150% 为 72px、200% 为 96px。第一版只留了 48px，在 125% 缩放的笔记本上必然被遮住。

因此 `:root` 定义 `--bottom-safe: 112px`（覆盖 200% 缩放的 96px，再留 16px 余量），作用于 `main.layout` 的 `padding-bottom`。实测滚到底部时最后一块内容距视口底边 158px（含页脚高度）。

另外在内容末尾加一行页脚（费用项数、数据不上传、文档位置）：既给出明确的"到底了"信号，也让底部空白不显得像渲染异常。

### 1.5.1.2 铺满宽度，不留空白

界面必须用满可用宽度。曾出现过"内容只占左半屏、右侧大片空白"的问题，来源是三处人为限宽：

| 位置 | 原做法 | 后果（1920px 屏幕） | 改法 |
|---|---|---|---|
| 页面容器 | `max-width: 1680px` | 两侧各留 120px | 放宽到 2400px（只在超宽屏生效） |
| 11 术语对比表 | `max-width: 1200px` | 面板右侧空白 **416px** | 去掉限宽，`width: 100%` |
| 结果三张卡 | 卡宽上限 360px 且左对齐 | 右侧数百 px 空白 | `repeat(auto-fit, minmax(280px, 1fr))` 等分铺满 |

当时给对比表限宽的理由是"数字别拉得太散"——这个取舍做反了：**宁可数字排得宽一点，也不能留半张面板的空白**。

**宽屏下更好的利用方式**：两张结果表（逐项明细、11 术语对比）在 ≥1700px 时并排，既用满宽度、又把表格拉回自然宽度，同时页面高度少一半。断点取 1700px 的依据是——并排后每张表都还能保持自然宽度（对比表最小约需 626px），低于此值并排会把表格压到小于最小宽度，反而触发横向滚动，与 1.5.1 的硬约束冲突。

实测（420 / 760 / 1024 / 1440 / 1600 / 1700 / 1920 七档）：无横向溢出，并排只在 ≥1700px 生效。

### 1.5.2 界面改版：从"数据倾倒"到可扫读

第一版界面被明确定为不可用，根因不是审美，是三条设计错误：

| 错误 | 症状 | 改法 |
|---|---|---|
| 所有信息同等视觉权重 | 8 个一模一样的白盒子，眼睛没有落点 | 分三层：顶栏关键数字 → 结论带 → 明细；只用一处强调色 |
| 录入界面按数据库字段铺开 | 费用项 11 列表格，编辑一行要左右滚，滚完忘了改的是哪行 | 主行只留 7 列（名称/节点/类别/计费/核算金额/归属/操作），其余字段收进可展开的明细行；首列固定 |
| 反馈回路断开 | 纵向布局后结果在下方几百像素，改数字看不到变化 | 顶栏吸顶常驻关键数字（卖方利润 / 买方总支付 / 提示数），改任何字段立刻变 |

另外三项具体改进：

- **数字加千分位**：`758100.00` → `758,100.00`，配合等宽数字（`font-variant-numeric: tabular-nums`）才能纵向比对
- **对比表分组与最优化**：按"卖方 / 买方 / 承担与风险"分组，最优值所在列高亮，首列固定
- **归属可视化**：费用项每行直接显示归属标签与计算后金额，待确认的行整行浅黄底——"这笔钱归谁"是系统核心价值，不该藏在结果表里

顶栏高度在窄屏（≤820px）会堆到 4 行，已加上媒体查询压缩，并允许 KPI 行横向滚动。

### 1.6 运行方式

**给使用者：双击 `trade-cost-engine.html` 即可。** 这是构建产物，样式与脚本全部内联，不需要安装任何东西、不需要联网、数据不出本机。

```bash
npm run build:single   # 生成根目录下的 trade-cost-engine.html
npm run serve          # 用静态服务打开该产物（不做任何注入，测的就是产物本身）
```

**浏览器兼容性**：使用者已在两款浏览器上实测通过。两点已知差异都做了降级处理——非 Chromium 浏览器没有"另存为"接口，会自动改为下载项目文件；浏览器禁用本地存储时草稿功能静默降级，不影响项目文件的读写。

**一个只有低版本浏览器才会暴露的坑**：打包目标声明为 `es2020`，但代码里用过 `Array.prototype.at()`——它是 **ES2022 的运行时方法，不是语法**，降级转换管不着，TypeScript 也不会报错，只有在低版本浏览器上才会抛 TypeError。已改为下标取值。同类运行时特性引入前需要先确认目标浏览器支持情况。

**给开发：**

```bash
npm install
npm run dev        # 开发模式，http://localhost:5173
npm test           # 引擎单测
npm run typecheck  # 类型检查
npm run audit      # 静态审查：未处理的界面字段/动作、声明了却无人产生的错误码与告警码
npm run build      # 产出静态文件到 dist/
npm run preview    # 预览 dist/
```

### 1.6.1 单文件构建的两个坑

`file://` 下浏览器把页面视为不透明源，外链 ES 模块会被 CORS 拦掉。因此单文件必须满足两个条件，二者都在构建脚本里有断言，缺一个就是白屏：

| 条件 | 原因 | 做法 |
|---|---|---|
| 脚本不能是 ES 模块 | 外链模块在 `file://` 下被 CORS 拦；Vite 生成的 HTML 模板无论输出格式都会写上 `type="module"` | `vite.config.ts` 设 `output.format: 'iife'`，内联时去掉 `type="module"`，并断言包内无 `import`/`export` 语法 |
| 脚本必须放在 `</body>` 之前 | 经典内联脚本**立即执行**；Vite 原本把脚本放在 `<head>`，靠模块的延迟执行才拿到 DOM。改成经典脚本后若仍在 head，执行时 `#app` 尚不存在，界面白屏**且不报错** | 构建脚本把脚本摘出来插到 `</body>` 前；`main.ts` 另加 `readyState` 就绪判断作为兜底 |

验证方式：把单文件用纯静态服务（无 HMR 注入）打开，确认零外部资源请求、界面完整、改数字即时联动。`file://` 协议本身被 Playwright 禁用，无法直接执行双击路径，因此改为在构建期断言上述两个条件。

### 1.7 界面冻结与界面不变量

**界面已冻结**：不再做视觉与交互调整。冻结不是一句承诺，而是 `tests/ui-invariants.test.ts` 这组契约测试——它锁定的每一条，都是本次开发中真实踩过的坑：

| 不变量 | 当初的故障 |
|---|---|
| 底部留白 ≥100px（`--bottom-safe`） | 滚到底部时最后一块内容被系统任务栏遮挡 |
| 页面容器不设窄限宽（≥2400px 或不设） | 内容只占左半屏，右侧大片空白 |
| 对比表不设限宽、按容器铺满 | 面板内右侧空白 416px |
| 对比表是"术语为行"的转置结构 | 11 个术语横排成 12 列，触发横向滚动 |
| 不使用横向滚动作为布局手段 | 表格被压扁、数据被遮挡且滚不动 |
| 费用项用自动换行的卡片而非多列表格 | 11 列表格编辑一行要左右滚动，滚完不知改的是哪行 |
| 结果表并排断点 ≥1700px | 低于此值并排会把表压到小于最小宽度，又挤出横滚 |
| 单文件构建保留三项自检 | `file://` 下白屏（模块被拦 / 脚本早于挂载点执行） |

要改这些行为，必须先在本文档写明理由、再改断言，不允许悄悄绕过。契约测试能挡住"改回去"这类回归，挡不住纯视觉走样——那部分只能靠人看。

**冻结后的例外（均记录在案）**：

1. 实现阶梯计费（4.8）时，在费用项卡片内新增了档位编辑器。理由：没有录入界面就无法使用；改动限于卡片内字段区。
2. 对比表的"承担范围"指标由**节点数**改为**费用项数**（节点数降为次要值）。理由：节点数无法区分 CIF 与 CFR——两者的差别在保险，而保险是费用类别不是节点（该局限由概念检测发现，见 6.4）。
3. 新增 **HS 税率表**面板（9.6），并在商品编码输入框上挂了一个候选编码下拉。理由：税率表是用户数据，没有维护界面就无法使用；面板沿用汇率行的形态（`.fx-row`）、默认折叠，未引入新的控件形态。三条契约断言（无横向滚动、卡片式费用项、铺满宽度）实测仍成立。
4. 费用项里计费参数那一栏的标签，由固定的"参数"改为**跟着计费方式变化**（金额 / 数量与单价 / 比率与基数 / 天数与费率 / 计费量）。理由见下：这属于用词错误而非样式偏好。

**关于第 4 条的说明**：原标签"参数"是实现视角的词。计费方式是"固定金额"或"实际金额"时，那个输入框里填的就是**金额本身**，标成"参数"等于把用户当程序员。这类用词问题应当按缺陷处理，不算破例。

### 1.8 容量与性能

计算本身很快：300 笔费用、11 种术语全比一遍 **34 ms**（约 20 次完整分析）；5000 条 HS 税率的查表 2.7 ms。**瓶颈全在界面重绘**——每次改动都会重建整个录入区。

实测曲线（浏览器，本机）：

| 费用项数 | 打开页面 | 改一个数字后重算+重绘 | DOM 节点 |
|---|---|---|---|
| 50 | 0.47 秒 | **0.07 秒** | 5.7 千 |
| 150 | 0.33 秒 | 0.47 秒 | 1.6 万 |
| 300 | 1.41 秒 | 1.69 秒 | 2.6 万 |

**曾有一个 O(n²) 的 DOM 缺陷**：费用项卡片里的"已含于"下拉，渲染时为每一笔费用列出其余全部费用项，300 笔费用产生约 **9 万个 option、11.5 万 DOM 节点**，页面加载超过 30 秒。改为渲染时只放当前值、获得焦点时才填充候选（`focusin` + `populateContainedIn`），300 笔的节点数降到 2.6 万、加载 1.4 秒。`tests/stress.test.ts` 有一条断言盯着"渲染出的 option 数随费用项数线性增长"，防止退回平方。

**实用容量为 100 项以内**（改一个数字的等待在 0.2 秒以内）。超出不会算错，只是有停顿；若将来真要处理上千项，需要把录入区改为虚拟滚动或折叠渲染，那是另一项工程。

## 2. 分层领域模型

三层结构，是本设计的骨架。

```
Layer 1  交易事实层 (Trade Facts)     —— 客观事实，与贸易术语无关
         Goods / Route / CostItem[]  / FxBook / TaxProfile / RuleSet

Layer 2  方案层 (Scenario)            —— 贸易术语与商务选择
         Incoterm / Quote / Overrides / FxSelection / BaseCurrency

Layer 3  结果层 (AnalysisResult)      —— 由 Engine 计算产出，只读
         EnrichedItems / Seller / Buyer / Risk / Warnings
```

**核心原则：同一套交易事实 + N 个方案 → N 份结果 → 对比矩阵。**

若按「一笔交易绑定一个 Incoterm」建模，方案对比功能将无法在不重写数据层的前提下实现。

### 2.1 实体清单

| 实体 | 层 | 职责 |
|---|---|---|
| `Trade` | 1 | 一笔交易：买卖双方、货物、路线、全部费用项 |
| `Goods` | 1 | 商品名称、数量、单位、成交货值、**卖方货物成本**、征税率、退税率、退税主体类型（见 11.4、9.5） |
| `CostItem` | 1 | 一笔费用的完整描述（见第 4 节） |
| `FxBook` | 1 | 某类型汇率的一张汇率表（见第 5 节） |
| `TaxProfile` | 1 | 一套税务规则（税率表、完税价构成规则） |
| `RuleSet` | 1 | 一套 Incoterms 规则表 + 特殊条件规则 |
| `Scenario` | 2 | 一个分析方案：术语 + 报价 + 覆盖项 + 汇率选择 |
| `Quote` | 2 | 成交报价：金额、币种、所含费用项 |
| `AnalysisResult` | 3 | 单方案计算结果 |
| `Comparison` | 3 | 多方案对比矩阵 |

### 3.1 贸易节点（11 个，固定）

```ts
type TradeNode =
  | 'SELLER_PREMISES'        //  1 卖方场所
  | 'INLAND_TRANSPORT'       //  2 出口国内陆运输
  | 'EXPORT_CLEARANCE'       //  3 出口清关
  | 'ORIGIN_TERMINAL'        //  4 起运地港口/机场
  | 'CARRIER_HANDOVER'       //  5 承运人接管
  | 'MAIN_CARRIAGE'          //  6 国际主运输
  | 'DESTINATION_TERMINAL'   //  7 目的地港口/机场
  | 'IMPORT_CLEARANCE'       //  8 进口清关
  | 'IMPORT_DUTIES'          //  9 进口关税及税费

每个 `CostItem` 必须绑定节点。节点是责任判定的**兜底**依据，不是主依据。

**注意：保险不是贸易节点，而是费用类别（`INSURANCE`）。** 保险费发生在主运输期间，但由哪一方负担取决于术语（CIF / CIP 归卖方，CFR / CPT 归买方），因此规则表按费用类别匹配保险，不绑定节点。

### 3.2 责任与角色

```ts
type Responsibility = 'SELLER' | 'BUYER' | 'SHARED' | 'CONDITIONAL';

type ResponsibilitySource =
  | 'USER_OVERRIDE'      // 用户显式指定
  | 'CONTRACT'           // 合同约定
  | 'INCOTERM_RULE'      // Incoterms 规则（含条件维度）
  | 'SPECIAL_CONDITION'  // 规则表未覆盖的事实兜底
  | 'TRADE_NODE'         // 节点弱推断
  | 'UNRESOLVED';        // 无法判定
```

**三个必须分离的概念**（不可互相推导，各自独立存储）：

| 概念 | 字段 | 含义 |
|---|---|---|
| 费用承担 | `responsibility` | 这笔费用最终由谁负担（经济归属） |
| 风险转移 | `risk_point`（方案级）+ `risk_relation`（费用级） | 货物灭失损坏风险在何处转移 |
| 实际付款方 | `payment_party` | 谁把钱付出去（可能是代垫） |

另加第四个字段 `economic_bearer`：当 `payment_party` 与 `responsibility` 不一致时（卖方代垫），记明谁是经济承担者。四者是四种不同的关系，UI 与结果表都必须分别展示。

## 4. CostItem 完整字段模型

### 4.1 类型定义

```ts
interface CostItem {
  // ---- 标识 ----
  cost_id: string;
  cost_name: string;
  cost_category: CostCategory;
  trade_node: TradeNode;
  location?: string;              // 具体地点，参与特殊条件判断
  timing?: {
    date?: DateStr;               // 单一时点费用
    start?: DateStr;              // 期间费用（天数计费）
    end?: DateStr;
    phase?: 'PRE_SHIPMENT' | 'IN_TRANSIT' | 'POST_ARRIVAL';
  };

  // ---- 计价 ----
  pricing_method: PricingMethod;
  amount?: Decimal;               // FIXED / ACTUAL 的原始金额
  unit?: string;                  // PCS / CTN / KG / CBM / TEU / DAY / SET
  quantity?: Decimal;
  rate?: Decimal;                 // QTY_X_UNIT 的单价；PERCENT 的比率（0.008 = 0.8%）
  days?: Decimal;                 // PER_DAY 的天数（可由 timing 推导）
  day_basis?: 'CALENDAR' | 'WORKING';
  calculation_base?: BaseRef;     // PERCENT 的计算基数引用
  tiers?: Tier[];                 // 阶梯收费档位，见 4.8
  tier_mode?: TierMode;           // MARGINAL 累进 | FLAT 分档，默认累进
  tier_basis?: TierBasis;         // QUANTITY 按数量 | DAYS 按天数，默认数量
  tier_charge_lower?: boolean;    // 分档时按空运规则与高一档择低

  // ---- 币种与汇率 ----
  currency: CurrencyCode;         // 原始币种
  fx_rate?: Decimal;              // 显式汇率（1 原始币种 = ? 核算币种）
  fx_type: FxType;                // 汇率类型
  fx_date?: DateStr;              // 汇率日期
  base_currency: CurrencyCode;    // 统一核算币种（来自方案）
  base_amount?: Decimal;          // [引擎输出] 换算后金额

  // ---- 税务 ----
  tax_included: boolean;          // 原始金额是否已含税
  tax_rate_ref?: string;          // 关联税率条目

  // ---- 归属（引擎输出，可被用户覆盖）----
  responsibility: Responsibility;
  responsibility_source: ResponsibilitySource;
  payment_party?: Party;
  economic_bearer?: Party;

  // ---- 报价与去重 ----
  included_in_quoted_price: boolean;  // 已含于成交报价
  contained_in_cost_id?: string;      // 已含于另一笔费用（如 THC 含在海运费报价中）
  dedup_group?: string;               // 同一笔实物流费用的分组键

  // ---- 风险 ----
  risk_relation?: RiskRelation;

  // ---- 元数据 ----
  is_custom: boolean;             // 用户自定义费用，系统不认识名称也必须能算
  source: 'USER' | 'DERIVED';     // DERIVED = 由系统推导生成（如 CIF 保险费）
  notes?: string;
}
```

### 4.2 相对需求新增的字段（重要）

**两种"已包含"必须分开。** 它们语义不同，混用会导致重复计算防不住：

| 字段 | 含义 | 典型场景 |
|---|---|---|
| `included_in_quoted_price` | 该费用已打进**成交报价**（Quote.amount） | CIF 报价 108,300 中已含运费 8,000 |
| `contained_in_cost_id` | 该费用的金额已含在**另一笔费用**的报价里 | 海运费报价已含起运港 THC，用户又单独录了一笔 THC |

第二种是实务中最常见的重复计费来源，仅靠 `included_in_quoted_price` 拦不住。

**另外两个字段各自对应一类重复计算：**

| 字段 | 含义 | 不设该字段的后果 |
|---|---|---|
| `is_goods_value` | 该项代表货物本身的**价值**，用于报价构成与海关完税价格 | 报价拆解中录了货值 100,000，卖方成本汇总又按 `seller_goods_cost` 计一次采购成本，货值被重复计算 |
| `includes_port_charges` | 该笔主运输报价**已声明包含港口操作费**（THC） | 无法识别"海运费已含港杂费、用户又单独录了一笔港杂费"这种重复计费 |

### 4.3 计算基数引用

```ts
type BaseRef =
  | { kind: 'GOODS_VALUE' }                // 货值
  | { kind: 'QUOTE_AMOUNT' }               // 报价总额
  | { kind: 'COST_ITEMS'; ids: string[] }  // 指定费用项之和
  | { kind: 'CUSTOMS_DUTIABLE_VALUE' };    // 完税价格（由税费引擎计算，见第 9 节）
```

`calculation_base` 中引用其他费用项或完税价格，会在引擎中产生**依赖边**，引擎必须按依赖顺序计算并检测环形依赖（第 10 节）。

**基数与币种的口径**：基数一律按核算币种计算，因此按百分比计费的费用项本身必须使用核算币种，否则基数和金额会脱节。引擎对此直接报错 `PRICING_CURRENCY_MISMATCH`，不做隐式换算。其他计费方式按各自币种计价后再换算到核算币种。

### 4.4 计价归一化公式

| pricing_method | gross_amount（原币） |
|---|---|
| `FIXED` | `amount` |
| `ACTUAL` | `amount`（用户已给出最终金额，跳过推导） |
| `QTY_X_UNIT` | `quantity × rate` |
| `PERCENT` | `resolveBase(calculation_base) × rate` |
| `PER_DAY` | `days × rate` |
| `TIERED` | 见 4.8：累进取各档分段之和，分档取全量 × 所在档费率（可择低） |

币种换算：`base_amount = gross_amount × fx_rate`。

### 4.5 费用录入：预设字典与自由录入

系统对费用名称不设白名单，**任何名称都能算**：归属判定只看 `trade_node`、`cost_category`、`occurrence_reason` 与术语，不看名称（见 6.3）。录入提供两条路径：

| 路径 | 用途 | 实现 |
|---|---|---|
| 预设字典 | 常见费用的名称、节点、类别、计费方式一键填入，省去重复打字 | `src/data/cost-presets.ts`，内置 40 余项，支持按名称与别名搜索 |
| 自由录入 | 字典里没有的费用：只要求指定节点与类别，其余字段自由填写 | `customCostItem()`，`is_custom = true` |

预设字典按节点覆盖：

- **商品与包装**：货值、包装费
- **出口国内陆运输**：内陆运费、拖车短驳、加固费
- **出口手续**：报关费、商检费、熏蒸费、产地证费、产品认证费、出口许可证、第三方验货费、单证费
- **起运地港口/机场**：订舱费、港杂费(THC)、铅封费、提单文件费、VGM 申报、美线申报(AMS/ISF)、装箱场站费、仓储费、出口查验费
- **国际主运输**：海运费（含"全包价"变体）、空运费、海运附加费、燃油附加费、铁路运费
- **保险**：货物运输保险费、战争险附加费
- **目的地**：港杂费、代理费、滞箱费/滞期费、仓储费、查验费、进口报关代理费、进口单证费、内陆运输费、送货上门费、卸货费
- **其他商务费用**：代理佣金、银行费用、出口信用保险费

**关键：预设只填节点与类别，不决定归属。** 归属仍由规则引擎按术语判定，因此同一个"订舱费"在 FOB 下归买方、在 CIF 下归卖方，不需要两套预设。

两条写进字典的实务提醒：

1. **出口信用保险不是货物运输保险**，不计入海关完税价格，因此归入自定义类别而不是保险类别——否则它会被算进完税价格。
2. **集装箱班轮条款下港杂费常已含在海运费报价中**，字典为此提供"海运费（全包价，含起运港港杂费）"这一预设，带上 `includes_port_charges` 标记，配合独立港杂费项即可触发重复计费告警。

### 4.6 发生原因（OccurrenceReason）

```ts
type OccurrenceReason =
  | 'NORMAL_OPERATION'        // 正常作业（默认，不参与判定）
  | 'SELLER_FAULT'            // 卖方原因：单证错误、包装不合格、迟延交货、申报不实
  | 'BUYER_FAULT'             // 买方原因：未及时提货、未及时开证或付款
  | 'CARRIER_FAULT'           // 承运人原因：甩柜、船期延误
  | 'CUSTOMS_INSPECTION'      // 海关查验
  | 'REGULATORY_REQUIREMENT'  // 法定检验检疫或认证要求
  | 'FORCE_MAJEURE';          // 不可抗力
```

这一维度存在的理由：**滞箱费、滞期费、仓储费、查验费这几类费用，单看节点判断不出归属。** 同样是目的港滞箱费，因买方未及时提货产生就归买方，因卖方单证错误产生就归卖方。

四个取值的行为并不相同：

| 取值 | 是否参与判定 | 归属结果 |
|---|---|---|
| `SELLER_FAULT` | 参与，**优先于术语** | 卖方 |
| `BUYER_FAULT` | 参与，**优先于术语** | 买方 |
| `CARRIER_FAULT` / `FORCE_MAJEURE` | 不参与 | 先按术语由承担方垫付，引擎提示"可向承运人索赔"，不替用户决定 |
| `CUSTOMS_INSPECTION` / `REGULATORY_REQUIREMENT` | 不参与 | 归属取决于发生在哪一侧的清关，由节点规则处理 |

**过错责任优先于术语的费用划分**是这一层的核心规则，符合实务：卖方单证出错导致目的港产生的费用，即便术语是 FOB 也归卖方。

### 4.7 自定义费用为什么必须能算

需求中"自定义费用不能因为系统不认识费用名称就无法计算"这一条，落到实现上是三条约束：

1. **计费方式与名称解耦**：六种计费方式对任意费用项一视同仁
2. **归属判定不看名称**：只看节点、类别、发生原因与术语
3. **自由录入不要求预先登记**：`customCostItem()` 只要求节点与类别

### 4.8 阶梯计费

实务里有两种"阶梯"，含义完全不同，因此做成显式的 `tier_mode`，不做隐式推断：

| 模式 | 含义 | 典型场景 |
|---|---|---|
| `MARGINAL` 累进 | 每档费率只作用于落在该档内的那部分数量（类似个人所得税） | 滞箱费：前 7 天免费、第 8–15 天每天 120、第 16 天起每天 200 |
| `FLAT` 分档 | 由计费量所在的档决定一个费率，**整个数量**都按这个费率算 | 空运重量等级运价（N / +45 / +100 / +300 …） |

```ts
interface Tier {
  up_to: Numeric | null;   // 区间上界（含）；null 表示"以上"
  rate: Numeric;           // 该档费率
}
```

**计算规则**（设计文档 4.4 的 `TIERED` 行）：

```
MARGINAL: Σ 各档 (落在该档内的数量 × 该档费率)
FLAT:     计费量 × 所在档费率
```

**空运重量等级运价的"择低"规则**：实际重量与更高分界点重量比较，取低者。勾选 `tier_charge_lower` 后：

```
费用 = min( 实际计费量 × 所在档费率,
           各更高档位的「最小计费量 × 该档费率」 )
```

例：档位 0–45 每公斤 35、45–100 每公斤 30.5，货量 40kg
→ min(40 × 35 = 1,400, 45 × 30.5 = 1,372.5) = **1,372.5**

这条规则同时解决了档位边界归属问题：按"上界含于本档"的约定，45kg 正好落在 0–45 档会算出 45×35 = 1,575，但择低规则会把它拉回 45×30.5 = 1,372.5，与空运惯例一致。

**校验（一律报错，不猜）**：无档位、出现两个无上界档位、上界重复或非递增、费率为负、计费量超出最后一个有上界的档位。档位乱序填写是允许的（引擎会排序），但上述结构问题必须由用户改对。

**录入**：费用项卡片在计费方式为"阶梯"时出现档位编辑器——每行显示区间（下界由上一档推出，不需要用户填两遍）、上界、费率；上界留空即"以上"。切换计费方式不会清空已填档位。

**一个录入陷阱**：分档 + 择低时，若更高的档位费率还是 0（预设填的占位值），"取低"会取到 0，整笔费用归零。数学上完全正确，但十有八九是没填完。引擎不改这个计算，改在录入处就地提示"有 N 个档位费率为 0，会使整笔费用变成 0"。

**预设**：字典中的"空运运费（重量等级运价）"已按行业惯例预填分界点 45 / 100 / 300 / 500 / 1000，并默认勾选"按高一档择低"，只需填费率。

## 5. FX Engine

### 5.1 汇率簿结构

```ts
interface FxBook {
  id: string;
  name: string;              // "2026-09 市场汇率" / "XX 合同汇率"
  type: FxType;              // MANUAL | CONTRACT | MARKET | CUSTOMS
  date: DateStr;             // 汇率生效日期
  rates: Record<string, Decimal>;  // { "USD/CNY": "7.0512", "EUR/USD": "1.0840" }
}
```

一个项目可持有多个 `FxBook`，按 `type` 分组。**海关汇率按月锁定**：`CUSTOMS` 类型的汇率簿带 `valid_from` / `valid_to`，同一月份内取同一本。

### 5.2 汇率解析顺序（逐级，不隐式回退）

```
1. CostItem.fx_rate          （用户对该笔费用显式指定 → 最高优先）
2. Scenario.fx_selection     （方案级：指定用哪本汇率簿）
3. 按 item.fx_type 找对应类型的汇率簿，取日期最近的一本
4. 找不到 → 报错，不猜
```

### 5.3 硬性约束

- `MARKET` / `CONTRACT` / `CUSTOMS` 三种类型**互不代替**。若某笔费用声明使用海关汇率而项目中无海关汇率簿，引擎报缺失错误，不退回商业汇率。
- 税费引擎（第 9 节）**强制**使用 `CUSTOMS` 类型汇率，不读商业汇率。
- 汇率换算结果保留 6 位小数，展示 2 位。
- 结果中每个金额都必须可追溯到「原始金额 + 币种 + 汇率 + 汇率类型 + 汇率日期」。

## 6. Incoterms Rule Engine

### 6.1 规则表结构

规则表是**数据**，不是代码分支。

```ts
interface CostResponsibilityRule {
  id: string;
  trade_node?: TradeNode;          // 省略 = 适用任意节点
  cost_category?: CostCategory;    // 省略 = 该节点下任意类别
  conditions: Condition[];         // 全部满足才匹配；空数组 = 无条件
  responsibility: Responsibility;
  note: string;                    // 依据说明，结果中展示给用户
}

interface IncotermRule extends CostResponsibilityRule {
  incoterm: Incoterm;
}

/** 第二级：合同约定。至少给出一个匹配条件，否则拒绝加载 */
interface ContractClause {
  id: string;
  cost_id?: string;
  cost_category?: CostCategory;
  trade_node?: TradeNode;
  cost_name_contains?: string;     // 用于覆盖系统不认识的费用名称
  responsibility: Responsibility;
  note: string;
}

interface IncotermsRuleSet {
  id: string;
  version: string;
  rules: IncotermRule[];
  special_facts?: CostResponsibilityRule[];  // 第三级：规则表未覆盖的事实兜底
  contract_clauses?: ContractClause[];
  node_fallbacks?: NodeFallback[];           // 第五级：贸易节点兜底
}

type ShippingTerms =
  | 'LINER' | 'UNDER_TACKLE' | 'STOWED' | 'TRIMMED' | 'STOWED_TRIMMED' | 'EX_SHIP_HOLD' | 'BULK';

type Condition =
  | { kind: 'DELIVERY_PLACE'; is: 'SELLER_PREMISES' | 'OTHER' }
  | { kind: 'SHIPPING_TERMS'; is: ShippingTerms }
  | { kind: 'CLEARANCE_AGENT'; is: 'SELLER_ACTS_FOR_BUYER' }
  | { kind: 'LOADING_MODE'; is: 'FCL' | 'LCL' }
  | { kind: 'CARRIAGE_MODE'; is: CarriageMode };
```

**具体度由引擎计算，不作为规则字段手工维护**：

```
specificity = 条件数 × 100 + (有 cost_category ? 10 : 0) + (有 trade_node ? 1 : 0)
```

同分时取声明顺序在前的一条。这样"条件更具体的规则优先、带类别的规则优先于只认节点的规则"是确定的，不需要人工维护优先级数字。

**四条实现上的硬性要求：**

1. **同一个词在不同节点含义不同。** 装货变形（`STOWED` / `TRIMMED` / `STOWED_TRIMMED`）作用于起运港，卸货变形（`LINER` / `EX_SHIP_HOLD`）作用于目的港，必须以节点为准判断。FOB 装船费的完整分支：`LINER` → BUYER、`UNDER_TACKLE` → BUYER、`STOWED` / `TRIMMED` / `STOWED_TRIMMED` → SELLER、无条件 → SELLER。**注意方向：FOB 班轮条件下装船费已含在运费中，由买方负担，不是卖方。**

2. **事实缺失时条件不成立。** 用户没填交货地点或运输条款变形时，带条件的规则不会命中，会落到下一条更粗的规则上。禁止因为"用户没填"就默认某个分支。

3. **保险是费用类别（`INSURANCE`），不是贸易节点。** 11 个贸易节点里没有保险节点，规则表按 `cost_category` 匹配保险费且不绑定节点，这样用户把保险费录在起运地或主运输节点下都能命中。

4. **规则表要完整，不依赖通配。** 每个术语生成全部 11 个节点的基础规则（11 × 11 = 121 条），例外规则单独列出并优先命中。规则表因此可以逐条审计，不存在"某节点没人管"的隐式缺口。

### 6.2 判定算法（优先级降级）

```
resolveResponsibility(item, scenario, ruleSet):

  # 1 用户显式指定 / 合同约定
  if override := scenario.overrides[item.cost_id]        → USER_OVERRIDE
  if clause := contract.match(item, scenario)            → CONTRACT

  # 2 发生原因（过错责任）：仅当费用项显式记录了非正常作业的原因
  if item.occurrence_reason ∉ {未填, NORMAL_OPERATION}:
      if reasonRule := ruleSet.reason_rules.match(...)   → OCCURRENCE_REASON

  # 3 Incoterms 规则（含条件维度）
  matched := ruleSet.rules
      .filter(incoterm == scenario.incoterm)
      .filter(trade_node == item.trade_node)
      .filter(cost_category 匹配或未限定)
      .filter(所有 conditions 成立)
      .sortBy(specificity DESC, 声明顺序 ASC)
  if matched 非空 → INCOTERM_RULE（取第一条）

  # 4 特殊条件兜底（规则表未覆盖的事实）
  if fact := ruleSet.specialFacts.match(item, scenario)  → SPECIAL_CONDITION

  # 5 贸易节点弱推断
  if fallback := nodeFallback(scenario.incoterm, item.trade_node, scenario.carriageMode)
      → TRADE_NODE（confidence = LOW）

  # 6 无法判定
  → CONDITIONAL / UNRESOLVED
```

**与需求原顺序的差异**（两处）：

1. **增加「发生原因」层，且置于 Incoterms 规则之前。** 这是需求中"地点 + 时间/节点 + 发生原因 + Incoterm"四个维度里最容易漏掉的一个。过错责任优先于术语的费用划分：即便术语是 FOB，若目的港滞箱费是因卖方单证错误导致的，该费用仍由卖方承担。该层只在费用项显式记录了原因时才启用，未填则完全不介入。
2. **把「特殊条件」移到「贸易节点」之前**，贸易节点降为兜底。贸易节点只说明费用发生在哪里，信息量最低；班轮条款、代办授权这类事实约束比位置更具决定性。

### 6.3 严格禁止的写法

不得实现「费用名称 → Seller/Buyer」的映射表。理由：「仓储费」在不同节点、不同原因下归属完全不同（出口前仓储归卖方，目的港滞箱费归买方，中转仓储取决于条款）。费用名称只用于展示与分类，不参与归属判定。

### 6.4 11 个术语的规则要点

风险转移与责任划分的基准事实如下（规则表的种子数据）：

| 术语 | 风险转移点 | 出口清关 | 主运费 | 保险 | 进口清关/关税 | 装卸要点 | 运输方式 |
|---|---|---|---|---|---|---|---|
| EXW | 卖方场所、未装货、置于买方处置 | 买方 | 买方 | 买方 | 买方 | 装货由买方 | 任何 |
| FCA | 交给买方指定承运人 | 卖方 | 买方 | 买方 | 买方 | 卖方场所交货→装货归卖方；其他地点→卸货归买方 | 任何 |
| FAS | 装运港船边 | 卖方 | 买方 | 买方 | 买方 | 船边交付 | 仅海运/内河 |
| FOB | 装上船 | 卖方 | 买方 | 买方 | 买方 | 装船费依运输条款变形：班轮/吊钩下归买方，理舱/平舱归卖方 | 仅海运/内河 |
| CFR | 装上船 | 卖方 | 卖方 | 买方 | 买方 | — | 仅海运/内河 |
| CIF | 装上船 | 卖方 | 卖方 | 卖方（强制，最低 ICC(C)，保额 ≥ 合同价 110%） | 买方 | — | 仅海运/内河 |
| CPT | 交给承运人 | 卖方 | 卖方 | 买方 | 买方 | 风险与费用分离 | 任何 |
| CIP | 交给承运人 | 卖方 | 卖方 | 卖方（强制，ICC(A)，保额 ≥ 合同价 110%） | 买方 | 风险与费用分离 | 任何 |
| DAP | 目的地、未卸货 | 卖方 | 卖方 | 卖方（非强制） | 买方 | 卸货由买方 | 任何 |
| DPU | 目的地、卸货完成 | 卖方 | 卖方 | 卖方（非强制） | 买方 | 卸货由卖方（11 个术语中唯一） | 任何 |
| DDP | 目的地、未卸货 | 卖方 | 卖方 | 卖方（非强制） | 卖方 | 卸货由买方 | 任何 |

**概念已由测试锁定。** `tests/incoterm-concepts.test.ts` 把术语定义逐条写成断言：7 + 4 的运输方式分类、11 个术语各自的责任划分与风险转移点、以及术语之间的相对关系（EXW 责任最小、DDP 最大、DPU 唯一负责目的地卸货、CFR/CIF 与 CPT/CIP 只差保险、DAP/DPU 只差卸货）。规则表若与概念不符，测试会直接失败。

**一个已知的指标局限（已修正）**：对比表原先用"卖方承担节点数"表示承担范围，但它无法区分 CIF 与 CFR——两者的差别在保险，而保险是费用类别而不是贸易节点。现已改为以**承担费用项数**为主、节点数降为次要值。

**必须落到规则表中的关键分支：**

1. **EXW 出口清关由买方办理**，实务中常由卖方代办 → 必然触发 `USER_OVERRIDE` / `SPECIAL_CONDITION`，是覆盖功能的主要使用场景。
2. **FCA 双分支**：交货地点在卖方场所 vs 其他地点，装货/卸货责任翻转。
3. **FOB / FAS 的装船费与港杂费** 依赖运输条款变形（`LINER` / `UNDER_TACKLE` / `STOWED` / `TRIMMED` / `STOWED_TRIMMED` / `EX_SHIP_HOLD` / 散货）。同名变形在装货节点与卸货节点含义相反，必须按节点判定。
4. **CIF 与 CIP 的保险不同**：CIF 最低 ICC(C)，CIP 要求 ICC(A)。两者保额最低均为合同价 110%。保险费是**算出来的**（见 9.4），不是查表。保险按 `cost_category = INSURANCE` 匹配，不绑定节点。
5. **风险与费用分离有四个术语**：CFR / CIF（风险在装船时转移，费用到目的港）与 CPT / CIP（风险在交给承运人时转移，费用到指定目的地）。引擎必须能同时输出「风险已转移」与「费用归卖方」。
6. **DPU 是唯一卖方负责在目的地卸货的术语**。
7. **DDP 下卖方承担进口清关与关税**，但需提示部分国家实操不可行（卖方无法作为进口方）。
8. **FAS / FOB / CFR / CIF 仅适用海运及内河运输**。若方案声明的运输方式为 AIR/RAIL/ROAD，这些术语不得出现在候选中，已被选用则报错。

### 6.5 CONDITIONAL 的处理

无法判定时不得静默假设。输出：

```ts
interface ConditionalItem {
  cost_id: string;
  message: string;             // 固定文案，见下
  as_seller_total: Decimal;    // 假设归卖方时的总成本
  as_buyer_total: Decimal;     // 假设归买方时的总成本
  delta: Decimal;              // 两者差额
}
```

固定提示文案：

> 该费用无法仅依据 Incoterms 自动确定，请根据实际合同及费用产生原因确认。

超出需求的一点：对 CONDITIONAL 费用同时给出两种归属下的总成本差额。商务谈判真正需要的往往是"这一笔归谁，影响多少钱"，实现成本很低。

## 7. Risk Engine

风险引擎**不做成复杂引擎**，它是一张 11 条目的映射表加少量条件分支。

```ts
interface RiskRule {
  incoterm: Incoterm;
  conditions?: Condition[];
  risk_point: string;        // 风险转移点描述
  risk_transfer_node: TradeNode;
}
```

输出：

```ts
interface RiskResult {
  transfer_point: string;        // 如 "货物装上船时"
  transfer_node: TradeNode;
  separation: boolean;           // 风险与费用承担是否分离
  separation_note?: string;      // 分离时的说明
}
```

**硬性要求：`RiskResult` 与 `responsibility` 并列输出，禁止互相推导。**

- `CFR` / `CIF` / `CPT` / `CIP` 四个术语 `separation = true`：风险早已转移给买方，但主运费（CIF / CIP 另含保险）仍由卖方承担至目的地。
  - CFR / CIF：风险在**装运港装船时**转移，费用承担延伸到目的港
  - CPT / CIP：风险在**货物交给承运人时**转移，费用承担延伸到指定目的地
- 其余七个术语（EXW / FCA / FAS / FOB / DAP / DPU / DDP）风险与费用在同一节点同步转移。
- 每笔 `CostItem.risk_relation` 由引擎按 `trade_node` 与 `risk_transfer_node` 的相对顺序填充 `BEFORE_TRANSFER` / `AFTER_TRANSFER`，**交付点及其之前算转移前**（如 FOB 的装船作业仍在卖方风险期内），用于结果表的辅助列。
- 引擎提供 `separatedCostIds()`：列出"风险已转移给买方、但费用仍由卖方承担"的费用项。这四个术语最容易被误读的地方就是这一列。

## 8. Price / Inclusion Engine

### 8.1 报价结构

```ts
interface Quote {
  amount: Decimal;                  // 成交报价金额（按报价术语、报价币种）
  currency: CurrencyCode;
  incoterm: Incoterm;               // 报价所依据的术语
  included_cost_ids: string[];      // 报价中已含的费用项
  fx_rate?: Decimal;                // 报价币种 → 核算币种
  fx_type?: FxType;
  fx_date?: DateStr;
}
```

需求中提出的示例作为**回归测试用例**：

```
CIF Price = USD 108,300
  内含 Goods     100,000
  内含 Freight     8,000
  内含 Insurance     300
```

### 8.2 汇总口径定义

```
Seller Cost        = Σ 责任为 SELLER 的费用（base_currency；不含代表货值的费用项与采购成本）
Buyer Additional   = Σ 责任为 BUYER 的费用（已含于报价的除外）
Buyer Total Landed = Quote.amount(换算) + Buyer Additional
卖方利润           = Quote.amount(换算) − Seller Cost − 采购含税成本 + 实际出口退税 − 退税资金占用成本
                     （完整定义与口径说明见 9.5.4 与 11.4）
```

**税费归属必须分开累计。** `BuyerSummary` 中的 `duty_total` / `consumption_tax_total` / `vat_total` 是**买方承担**的税费，不是税费总额——DDP 下进口税费由卖方承担，此时买方口径的三项均为 0。曾经把总额记到买方头上，导致三个问题：买方卡片显示出他没付过的税、该列各项加不成"落地成本"、且"不含可抵扣税"口径凭空少掉一笔他从未支付的增值税。

术语无关的**税费总额**（对比表里那一列）由 `compare` 另行汇总所有派生税费项，与承担方无关——这与"完税价格与术语无关"是同一条性质。
```

### 8.3 去重算法

```
applyInclusionDedup(items, quote):

  # A 报价内含去重
  for item in items where item.included_in_quoted_price:
      if item.responsibility == SELLER:
          → 计入 Seller Cost；从 Buyer Additional 中排除
      if item.responsibility == BUYER:
          → 标记 CONFLICT("报价已含该费用，但按术语应由买方承担，请确认是否为卖方代垫")

  # B 费用内含去重（contained_in_cost_id）
  for item where item.contained_in_cost_id:
      → 不参与任何汇总，仅作为父费用的构成明细展示
      → 若 item 未标记 contained_in 但 dedup_group 与另一项相同，标记 POSSIBLE_DUPLICATE

  # C 港口操作费校验（实务高发）
  if 主运输费用声明已含起运港/目的港操作费
     且存在独立的同节点操作费费用项
     且该项未标记 contained_in_cost_id
     → 标记 WARNING("海运费报价通常已含港杂费，请确认是否重复计费")
```

**关键点：去重方向随术语变化。** 同一笔"海运费 8,000"，在 CIF 方案下是卖方成本、买方不重复计；在 FOB 报价 + 卖方自愿另付运费的方案下则是卖方额外支出。因此去重逻辑挂在「本次方案的报价所含集合」上，而非单纯挂在 `CostItem` 的布尔字段上。

**权威口径规则**：`Quote.included_cost_ids` 一旦非空即为**权威**，完全覆盖费用项上的 `included_in_quoted_price` 标记；只有报价未声明清单时（单方案手工录入情形）才退回使用费用项标记。

这条规则不是可选项。跨术语对比时同一个费用项在不同术语下是否"已含于报价"本来就不同，若两处口径取并集，那么一笔在 CIF 下已含的运费，换到 EXW 下仍会被当成已含，买方额外成本会凭空少一块。报价内含清单在按术语生成方案时由责任判定推导：**报价覆盖的正是卖方在该术语下承担的费用**。

## 9. Tax Engine（默认按 D1 采用中国海关口径）

### 9.1 结构

税务层实现为可插拔 `TaxProfile`，内置 `china-customs` 规则档。

```ts
interface TaxProfile {
  id: string;                       // "china-customs"
  import: {
    dutiableValueBasis: 'CIF';      // 完税价格以到岸价为基础
    insuranceFallbackRate?: Decimal;// 无法确定保险费时按 (货价+运费) × 3‰
    dutyRates: TaxRateTable;        // 按 HS 编码/商品分类
    dutyExemptionThreshold?: Decimal;// 关税税额低于阈值免征（默认 50 元，可关闭）
    consumptionTax?: ConsumptionTaxRule;  // 仅对特定消费品
    vatRate: Decimal;               // 一般货物 13%
    vatDeductibleForBuyer: boolean; // 影响 landed cost 双口径
  };
  export: {
    dutiableValueBasis: 'FOB';        // 出口关税（多数商品为 0）
    dutyRates: TaxRateTable;
    rebate: RebateProfile;            // 出口退税，见 9.5
  };
  customsFx: { bookType: 'CUSTOMS'; lockPeriod: 'MONTHLY' };
}
```

### 9.2 计算链（有向依赖，必须拓扑排序）

```
Step 1  完税价格 = 货值 + 运抵境内输入地点起卸前的运费 + 保险费
                    ↑ 引用 GOODS_VALUE、MAIN_CARRIAGE、INSURANCE 三类费用项
Step 2  关税     = 完税价格 × 关税税率
Step 3  消费税   = (完税价格 + 关税) ÷ (1 − 消费税率) × 消费税率     [仅应税消费品]
Step 4  增值税   = (完税价格 + 关税 + 消费税) × 增值税率
```

**这是本系统技术上最容易写错的地方**：税费基数不是把费用简单相加，而是有法定构成。因此 `calculation_base` 必须支持引用其他费用项与 `CUSTOMS_DUTIABLE_VALUE`（第 4.3 节），引擎必须按依赖顺序计算并检测环形依赖。

**完税价格按海关适用汇率折算，不用商业汇率。** 货值、运费、保险费若以外币计，每一项都要单独按 `CUSTOMS` 类型的汇率折算成海关计征币种，然后相加。这意味着完税价格不等于这些费用在账上的核算币种金额之和——两套汇率体系必须各走各的。若缺少海关适用汇率，引擎不静默套用商业汇率，而是给出 `CUSTOMS_FX_FALLBACK` 告警并在结果中标注该口径不一致。

### 9.3 汇率强制约束

税费相关的所有换算**强制**使用 `CUSTOMS` 类型汇率簿，且按月度锁定（同一月份内使用同一本）。商业汇率、合同汇率不得参与任何税费计算。

### 9.4 保险费的计算（而非查询）

CIF / CIP 下保险费由卖方投保，金额需计算：

```
保险金额 = 合同价 × 110%
保险费   = 保险金额 × 保险费率
```

引擎在 CIF / CIP 方案下可**自动生成**一笔 `source = 'DERIVED'` 的保险费费用项（`is_custom = false`，用户可覆盖）。CIF 险别默认 ICC(C)，CIP 默认 ICC(A)，两者在规则表与展示中必须区分。

### 9.5 出口退税（Export VAT Rebate）

> 中国出口商有相当比例靠出口退税维持利润。退税是**利润的主要构成项之一**，必须进入利润模型，不能只在备注里提一句。

#### 9.5.1 两种退税主体，计算路径完全不同

```ts
type RebateEntityType = 'TRADING' | 'MANUFACTURER';

interface RebateProfile {
  entityType: RebateEntityType;
  rebateRates: TaxRateTable;     // 按商品：退税率（0% ~ 13%）
  vatRates: TaxRateTable;        // 按商品：征税率（一般 13%）
  rebateLagDays?: number;        // 退税到账周期，默认不启用
  sellerFundingRate?: Decimal;   // 卖方资金成本率（年化），启用周期时使用
}
```

| 主体 | 办法 | 退税计税依据 | 退税额 |
|---|---|---|---|
| 外贸企业（购进出口） | 免退税 | 购进货物的增值税专用发票金额（不含税） | 不含税采购金额 × 退税率 |
| 生产企业（自产出口） | 免抵退税 | 出口货物离岸价（FOB，折人民币） | min(FOB 价 × 退税率, 期末留抵税额) |

**结论：外贸企业路径下退税额取决于采购成本，与出口售价、贸易术语无关；生产企业路径下退税额挂钩 FOB 价，因而与贸易术语直接相关。** 两种主体在 11 术语对比中的结论可能不同，必须分开建模。

#### 9.5.2 退税基数是 FOB 价 —— 术语依赖性

生产企业路径以离岸价为退税基数。以 CIF / CFR / CIP / CPT 等含运费的术语成交时，须从成交价中扣除运费、保险费、杂费，还原为 FOB 价：

```
成交方式为 FOB            → FOB 价 = 成交价
成交方式非 FOB（含运保费） → FOB 价 = 成交价 − 运费 − 保险费 − 报关单杂费栏金额
```

**关键结论：同一个报价金额，用不同术语成交，FOB 基数不同，退税额也不同。** 即使采用 Anchor A（固定报价）也成立：

```
报价 108,300 以 CIF 成交 → FOB 基数 100,000 → 退税基数 100,000
报价 108,300 以 FOB 成交 → FOB 基数 108,300 → 退税基数 108,300
```

引擎必须实现「成交价 → FOB 价」的还原，且**扣除哪些费用由术语决定**（复用第 8 节报价内含费用与责任判定结果，不另建一套）。海运术语下，即便术语本身不含运费（如 FOB），若报关单成交方式填报为 CIF，仍须还原。

#### 9.5.3 征退税率差转入成本

退税率低于征税率时，差额部分不得免征和抵扣，须转入成本：

```
不得免征和抵扣税额 = 退税基数 × (征税率 − 退税率)
```

- 外贸企业：按采购不含税金额与其征税率计算
- 生产企业：按 FOB 价计算

外贸企业还有一种等价写法，实现时只用一种，避免双算：

```
可退税额     = 采购不含税金额 × 退税率
采购实际成本 = 采购含税金额 − 可退税额
```

#### 9.5.4 利润公式（含退税）

```
卖方利润(i) = 报价收入(i) − 卖方承担费用(i) − 采购含税成本
              + 实际出口退税(i) − 退税资金占用成本(i)

其中：采购含税成本 = 外贸企业的含税采购价 / 生产企业的生产成本（均含进项税）
```

**注意口径：只能二选一，混用会重复扣减。**

| 口径 | 公式 | 校验（采购含税 113、不含税 100、征 13% 退 9%） |
|---|---|---|
| A（实现采用） | − 含税成本 + 实际退税 | −113 + 9 = **−104** ✓ |
| B | − 不含税成本 − 不得免征和抵扣税额 | −100 − 4 = **−104** ✓ |
| 错误写法 | − 含税成本 + 退税 − 不得免征和抵扣税额 | −113 + 9 − 4 = −108 ✗ 多扣一次 |

`不得免征和抵扣税额` 因此**只作为展示指标**（说明有多少进项税没能退回），不参与利润扣减。它是"含税成本 − 不含税成本 − 已退税额"的差额。

**退税是现金流入，必须作为利润加项。** 结果中额外给出 `margin_ex_rebate`（不含退税的利润），用于展示利润对退税的依赖程度——这是中国出口商最关心的一个数。

#### 9.5.5 退税到账周期（可选）

退税通常在申报后 1–3 个月到账，构成资金占用。`rebateLagDays` + `sellerFundingRate` 启用后：

```
资金占用成本 = 出口退税 × 年化资金成本率 × 账期天数 ÷ 365
```

默认关闭，启用后作为一笔 `PER_DAY` 或 `ACTUAL` 的费用项计入卖方成本。

#### 9.5.6 消费税退税

出口应税消费品同时退还消费税，作为独立的退税条目处理，不并入增值税退税。

#### 9.5.7 退税风险与提示
| 情形 | 处理 |
|---|---|
| 退税率为 0 | 该商品不予退税，退税项为 0，提示用户 |
| 征退税率差 > 0 | 差额部分进成本，已在 9.5.3 体现 |
| 申报逾期 | 出口退税须在次年 4 月增值税纳税申报期截止前申报，逾期视同内销征税。结果中给出申报期限提醒 |
| 单证不齐 | 无有效增值税专用发票或报关单则无法退税，退税项按 0 计算并提示 |
| 生产企业留抵不足 | 免抵退税额受期末留抵税额限制，实际退税额可能小于理论值；v1 允许用户手工给定留抵税额，未给定则按理论值计算并明确标注为"上限值" |

### 9.6 HS 税率表

按商品编码查税率，替代"一个商品大类一个兜底税率"的粗粒度做法。

```ts
interface HsRateEntry {
  code: string;                 // 纯数字，通常 6–10 位；也可维护 2/4/6 位的上级编码
  description: string;
  duty_type?: DutyType;         // AD_VALOREM 从价 | SPECIFIC 从量 | COMPOUND 复合，默认从价
  duty_rates?: Partial<Record<DutyRateBasis, Numeric>>;   // 按口径分别维护
  specific_amount?: Numeric;    // 从量税的单位税额
  specific_unit?: string;       // 从量税的计量单位（如 千克、升、支）
  vat_rate?: Numeric;
  consumption_tax_rate?: Numeric;
}

interface HsRateTable {
  basis: DutyRateBasis;         // MFN 最惠国 | AGREEMENT 协定 | INTERIM 暂定 | GENERAL 普通
  entries: HsRateEntry[];
}
```

**编码逐级回退**：查询顺序 10 → 8 → 6 → 4 → 2，取最接近输入编码的上级。这是税则的实际用法——给每个 10 位编码单独维护税率很麻烦，通常只在 6 位或 8 位上维护，下级继承。编码里的点、空格等非数字字符会被忽略（`8518.30.00` 可以匹配 `851830`）。

**税率口径由用户显式指定，引擎不替用户选**——适用哪一档取决于原产国与贸易协定。回退链条上的每一步都必须说出来：

| 情况 | 处理 |
|---|---|
| 该编码未维护所选口径的税率 | 回退最惠国税率，提示用了哪一档 |
| 该编码完全未维护税率 | 回退商品大类的兜底税率，告警 |
| 编码不在表中 | 回退兜底税率，告警并提示核对归类 |
| 按上级编码命中 | 提示实际使用的是哪个上级编码 |
| 表中编码重复 | 告警（实际只按最后一条计算），请合并 |

**从量与复合税**：

```
从价：完税价格 × 税率
从量：数量 × 单位税额
复合：从价 + 从量
```

从量税需要商品数量与单位，三处一律报错、不做隐含处理：缺单位税额、缺数量（不按 0 处理）、计量单位与商品单位不一致（升 ≠ 箱，不做换算）。从量税下不再显示"关税税率"——从价税率为 0，如果拿商品大类的兜底税率显示一个不存在的税率，只会误导。

**未支持**：按完税价格高低二选一的"选择型复合税"（例如某些录像机：完税价格超过某金额则整体改按从量税）。遇到这类编码请按实际税额手工录入。

## 11. 核心功能：11 种术语的横向对比

> 本节是整个系统的核心，其余功能均服务于它。

### 11.1 核心场景

同一商品、同一数量、出口到同一目的地市场，因采用的贸易术语不同，卖方的成本与利润不同。系统要回答的问题是：

**这批货卖给这个市场，用哪一个 Incoterm 最赚钱？**

### 11.2 可比性问题（对比的第一原则）

不同术语下的报价金额本身**不可比**，因为买卖双方承担的义务范围不同。CIF 报价 108,300 与 FOB 报价 100,500 无法直接排序。唯一可比的是两个口径：

- **买方口径**：买方为该批货实际付出的全部成本（Buyer Total Landed Cost）
- **卖方口径**：卖方从该批货实际得到的净收入与利润

对比表必须同时给出这两列。任何仅比较"报价金额"的横向结论都是无效的。

### 11.3 比较基准（Anchor）——决定"利润"怎么算

"11 个术语下利润不同"有三种不同含义，取决于把什么视为不变量。三种都要支持：

```ts
type ComparisonAnchor =
  | { kind: 'FIXED_QUOTE'; quoteAmount: Decimal }        // A 固定报价金额
  | { kind: 'FIXED_MARKET_PRICE'; buyerTotal: Decimal }  // B 固定买方总支付
  | { kind: 'FIXED_MARGIN_RATE'; marginRate: Decimal };  // C 固定目标利润率
```

| 基准 | 固定什么 | 输出 | 适用场景 |
|---|---|---|---|
| A 固定报价 | 报价金额不变 | 各术语下卖方利润、买方实付 | 快速观察成本承担变化 |
| B 固定买方总支付 | 买方愿付的总价不变 | 各术语下报价金额、承担范围与风险（利润趋于一致，见 11.3.1） | 商务决策主场景（默认） |
| C 固定目标利润率 | 卖方利润率不变 | 各术语下应报多少钱 | 对外报价辅助 |

**B 是商务决策的主场景。** 同一批货买方只愿意付一个总价，卖方选择承担到哪一环，决定了报价与风险，而不是（在成本不随承担方变化时）总利润的高低。见下面的重要结论。

反推公式：

```
A: SellerCost(i) 由引擎直接计算，报价取给定值
C: quote(i) = (卖方承担费用 + 采购成本) ÷ (1 − 目标毛利率)      ← 不含出口退税的毛利率
B: 求解 quote(i) 使 BuyerTotal(i) = 目标买方总支付
   BuyerTotal(i)      = quote(i) + BuyerAdditional(i)
   BuyerAdditional(i) = 买方承担的报价外费用 + 进口税费
```

**关于迭代**：进口税费的基数是完税价格，而完税价格以**货物成交价**（`Goods.trade_value`）加运费保险费为基础，不随报价总额变化，因此正常情形下一步即可解出。只有存在以报价金额为基数的百分比费用项（如"按报价 3% 计佣"）时才真正需要不动点迭代：初值取 A 基准下的报价，收敛判据为相邻两轮报价差额 < 0.01，上限 50 轮；未收敛或解出负报价时，判定该术语在此基准下**不可行**，而不是返回一个近似值。

### 11.3.1 两个必须写进结果页的恒定量

实现阶段验证出来两条容易反直觉的结论，直接影响用户怎么看对比表：

**（1）进口税费总额与贸易术语无关。** 完税价格由货物成交价、运费、保险费构成，这三项是交易事实，不随术语变化。因此 11 个术语下关税、增值税、消费税的总额是同一个数，术语改变的只是**由谁承担**。对比表若显示各术语税费不同，说明数据录错了。

**（2）在 B 基准下，各术语的卖方利润会趋于一致。** 推导：

```
卖方利润 = 买方总支付 − 卖方承担费用 − 采购成本 + 退税
卖方承担费用 + 买方承担费用 = 全部费用之和（与术语无关）
⇒ 卖方利润 = 买方总支付 − 全部费用之和 − 采购成本 + 退税
```

只要"同一环节不论由谁操作、金额都相同"，上式右边就与术语无关，B 基准下各术语利润相同——术语改变的只是**报价金额**与**风险/承担范围**。利润差异只可能来自三个来源：

| 来源 | 说明 | 系统当前是否支持 |
|---|---|---|
| 术语引发的增量成本 | 如 CIF/CIP 的强制投保、DDP 必须发生的进口清关代理费 | 支持：把这类费用项录入即可，但它对双方都存在，需要用户自行判断哪些项只在某术语下发生 |
| 出口退税基数的术语依赖性 | 生产企业路径下退税基数为离岸价，A/C 基准下离岸价随术语变化 | 支持（见 9.5.2） |
| 同一环节的成本因承担方不同而不同 | 卖方自营运费可能低于买方自行安排的价格，这正是"术语套利"的来源 | **不支持自动建模**：一个费用项只有一个金额。若要用 B 基准评估套利空间，需分别录入双方各自的价格作为不同费用项 |

因此 B 基准确的价值在于回答"买方只肯付这个总价，我该报多少、承担到哪一环、风险落在谁头上"；而 A 基准（固定报价）才是直接观察利润随术语变化的口径。

### 11.4 利润的定义（含出口退税）

```
卖方利润(i) = 报价收入(i) − 卖方承担的全部费用(i) − 采购含税成本
              + 实际出口退税(i) − 退税资金占用成本(i)
```

（口径说明与常见错误写法见 9.5.4，不要在此叠加"不得免征和抵扣税额"。）

退税的完整计算见 9.5。**对中国出口商，忽略退税的对比结论可能是错的**：生产企业路径下不同术语的报价不同 → FOB 基数不同 → 退税额不同，这个差额足以改变最优术语的排序。对比结果同时给出 `margin_ex_rebate`（不含退税的利润），让人一眼看出利润里有多少是退税撑起来的。

必须区分两个"货值"，不可混用：

| 概念 | 含义 | 用途 |
|---|---|---|
| 成交货值（报价构成中的 goods 部分） | 对买方而言的货物价格 | 报价拆分、海关完税价格 |
| 卖方货物成本 `seller_goods_cost` | 卖方的采购价或生产成本 | 计算卖方利润 |

缺卖方货物成本则利润无从计算，因此 `Goods` 实体必须包含该字段。

## 12. 数据持久化

### 12.1 项目文件格式

```jsonc
{
  "schema_version": "0.1",
  "project": { "id": "...", "name": "...", "created_at": "...", "updated_at": "..." },
  "base_currency": "CNY",
  "fx_books":   [ /* FxBook[] */ ],
  "rule_set":   { "id": "incoterms2020", "version": "1.0" },
  "tax_profile":{ "id": "china-customs", "version": "1.0" },
  "trades":     [ /* Trade[]，含 goods / items */ ],
  "scenarios":  [ /* Scenario[] */ ],
  "comparisons":[ /* 保存的对比视图配置 */ ]
}
```

- 一个文件装下全部内容，可归档、可邮件发送、可纳入版本管理。
- `schema_version` + 迁移函数表，保证旧文件可升级打开。

### 12.2 持久化策略（三层）

| 层 | 载体 | 作用 | 可靠性 |
|---|---|---|---|
| 草稿 | `localStorage` | 每次改动自动保存，防止误关页面丢数据 | **不可作为权威来源** |
| 权威 | 项目文件（`.json`） | 用户显式打开/保存 | 唯一权威 |
| 交换 | 项目文件本身 | 归档、邮件发送、纳入版本管理 | — |

**为什么项目文件必须是权威来源**：`file://` 环境下的浏览器存储行为在各浏览器间并不一致（Firefox / Safari 对本地文件的存储与部分 API 有限制），且清缓存、换机器、换浏览器都会导致数据丢失。因此：

- "保存项目"在支持 File System Access API 的浏览器（Chrome / Edge）下弹出真正的系统另存为对话框并直接写盘；不支持的浏览器降级为下载文件
- 建议文件名会剔除 Windows 非法字符，避免浏览器截断
- 打开方式为文件选择器；项目文件版本不符时直接报错，不做静默修补——静默修补会让"看起来打开了"的项目悄悄丢数据
- 启动时若存在草稿会恢复，并在状态栏明确标注"已恢复上次编辑的草稿（尚未保存为文件）"，颜色为警示色，避免用户误以为已存盘

### 12.2.1 尚未实现（已知边界）

- **拖拽打开**：明确不做（评估后放弃，文件选择器已够用）
- **费用清单批量录入（CSV / 剪贴板）**：未做。这项极易出 bug——列顺序、单位、千分位、多币种、合并单元格、编码错位都会导致**静默错算**，比手工录入更危险。若要做，必须配"解析预览 + 逐行校验 + 明确报错"，不允许解析失败就跳过该行
- **草稿用 localStorage 而非 IndexedDB**：项目体积远小于 5 MB，localStorage 足够；换 IndexedDB 只是替换 `draft-store` 一个模块
- **单文件版在浏览器禁用本地存储时不会报错但也不保留草稿**：项目文件是权威数据源，草稿只是便利层，因此静默降级

### 12.3 无多设备同步（明确的取舍）

无服务器即意味着数据不会自动同步到另一台机器，只能通过项目文件手动传递。这是"无登录"的必然代价，不作为缺陷处理。

## 13. 校验清单

系统用两套互不混用的机制：

| 机制 | 用途 | 界面表现 |
|---|---|---|
| `EngineError` | **阻断计算** | 显示"无法计算"+ 编码与说明，不允许降级为猜一个值 |
| `Warning` | 算得出结果，但需要用户核对 | "校验与提示"面板按级别分列 |

**共同约定：声明了就必须有地方产生。** 不留"预留但从未触发"的编码——那会让读代码的人以为校验存在。`tools/audit.mjs` 检查双向一致性（声明未抛出、抛出未声明都会报错），当前 19/19 与 29/29 全部对得上。

### 13.0 空输入：一条必须专门盯住的缺陷类

用户在界面上清空任何一个数字框，传到引擎的是**空字符串**，不是 `undefined`。而 `??` 与 `=== undefined` 都不把空串当空值：

- `item.days ?? fallback` 遇到 `''` 会原样返回空串，绕过"没填"的判断
- `value === undefined || value === null` 同样放行空串

后果是空串一路流进 decimal.js，抛出 `[DecimalError] Invalid argument`——界面显示"未知错误"，还泄露了内部库的名字，用户完全不知道哪里没填。

三层防护，缺一不可：

| 层 | 做法 |
|---|---|
| 数值层 | `decimal.js` 的封装 `d()` 明确拒绝空串，并给出可读的报错 |
| 字段层 | 计价参数用 `isBlank()` 统一判断"没填"（空串 / null / undefined），报"缺少「单价」"这类信息 |
| 入口层 | `analyze()` 开头校验报价金额、成交货值、采购成本、商品数量，并顺带挡住带千分位或货币符号的输入 |

回归用例集中在 `tests/blank-inputs.test.ts`。

### 13.0.1 文案不许出现实现词汇

报错与标签是给外贸业务人员看的，不能出现 `QTY_X_UNIT`、`quantity`、`cost_id` 这类标识符。这条被指出过两次（费用项的"参数"标签、报错里的 `quantity`），因此：

- 计费方式的中文名放在 `src/domain/enums.ts`（`PRICING_METHOD_LABELS`），引擎与界面共用一份
- 费用项里计费参数那一栏的标签跟着计费方式走：金额 / 数量与单价 / 比率与基数 / 天数与费率 / 计费量
- `tests/pricing.test.ts` 有一条断言扫描报错文案是否含内部标识符
